## 1. 背景与目标

### 1.1 问题

当前全链路（后端 diff → 查看渲染 → 编辑重算 → 持久化）均为**全量处理**模式：

| 环节 | 现状 | 百万字表现 |
|------|------|-----------|
| 后端 diff | `diff_main` 一次性全量，`Diff_Timeout=0` | **实测 0.11–0.64s**（见 §17，无需分块） |
| 查看渲染 | `v-html` 全量拼 HTML + 全量 DOM | 浏览器卡顿/崩溃（**真瓶颈**） |
| 编辑重算 | 300ms 防抖后全量 `classifyEdit`（JS DMP） | 每次编辑 UI 阻塞（**真瓶颈**） |
| 持久化 | 草稿 localStorage + 后端明文 JSON 全量 | 超 5MB 配额、序列化慢 |

计划文档的 D5 决策结论是"不上 Worker 则限制文档 ≤10 万字"；第三期验收标准为"100 万字文档编辑流畅（<200ms 重算延迟）"。本方案即补齐这一缺口。

### 1.2 目标（验收锚点）

1. **100 万字**文档：对比全流程可完成（含首屏可见时间 <5s、总耗时 <60s）
2. 编辑模式下，每次编辑后**重算延迟 <200ms**（Worker 后台计算，UI 不阻塞）
3. 查看模式滚动流畅（虚拟化渲染，DOM 节点数 ≈ 可视区域，恒定）
4. 草稿/恢复能力在 100 万字下不丢失（IndexedDB 承载）
5. 现有 46 项前端测试 + 78 项后端测试全绿，新增分块等价性测试

### 1.3 设计原则

- **不改变 segment 数据格式**：分块 diff 产出与全量 diff 结构完全一致的 `Segment[]`，前端零感知
- **复用而非新建**：查看模式复用 CodeMirror 的虚拟行渲染与现有 decoration 管线，不引入第三方虚拟滚动库
- **渐进降级**：每一层都有"旧路径"兜底（Worker 不可用 → 主线程；分块失败 → 全量）
- **规模分级驱动**：不是一刀切，而是按文档规模选择路径

## 2. 现状瓶颈盘点（代码级事实）

### 2.1 后端

- `src_backend/diff_engine.py`：`diff_match_patch()` + `Diff_Timeout = 0` + `diff_main` 全量 + `diff_cleanupSemantic`。**性能预研结论：纯 Python DMP 在 100 万字量级性能极好（最坏 0.64s），不存在 O(n²) 退化问题**——本节不再是瓶颈（原假设错误，见 §17）
- `src_backend/main.py`：`CHUNK_SIZE = 50` 段/块；`phase` 仅 3 个固定点（parsing=10 / diffing=50 / done），diffing 无进度——**进度缺失本身影响小（diff 仅 0.64s），真正的传输/内存成本在前端全量收集**（§2.2）
- 上传无大小限制（仅扩展名校验）——仍是需要补的点（防内存 DoS）

### 2.2 查看模式

- `SplitView.vue` / `UnifiedView.vue`：`renderSplitColumns` / `renderSegmentsToHTML` 全量字符串拼接 + `v-html`，百万段生成 MB 级 HTML 与数十万 DOM 节点
- 全项目唯一的截断是 Sidebar 差异列表 `slice(0, 60)`

### 2.3 编辑模式

- `CodeMirrorDiff.vue`：300ms 防抖 → `classifyEdit(baseline, fresh)`（JS DMP 全量 diff）→ `buildDecoSet` 全量重建 + `rebuildDiffLayer` 全量重建 diff 层装饰
- `updateListener` 内 `update.state.doc.toString()` 在防抖回调中执行（频率已降，但百万字一次 toString 约 10–50ms，且全量 diff 本身阻塞 UI）
- `editor.ts`：`getEditedSegments()` 每次调用全量 classifyEdit；`editedStats` / `editedContexts` 两个 computed 都依赖它 → **渲染一次 = 全量 diff 一次**（高频触发点）
- `history()` 无栈上限；Widget 已有 >1000 字符截断保护

### 2.4 持久化

- segments 已存 IndexedDB（`indexeddb.putAll('segments', chunks)`）——基础是好的
- 编辑草稿存 localStorage（`cmp_edit_*`），超容量剥离 segments 降级、后端兜底——**100 万字时 editText+baseline 本身约 4–8MB（UTF-16），localStorage 5MB 配额直接爆，连"轻量版"都可能写不进**
- 后端 autosave：明文 JSON 全量（含 segments），每次保存序列化百万段约数百 ms 级
- `computeDraftKey()`：FNV-1a 对 baseline 全文 hash——百万字每次 enterEdit 一次 O(n)

## 3. 总体架构

按"规模分级 × 分层改造"两个维度组织：

```
                 ┌──────────────────────────────────────────┐
                 │          文档规模分级 (L0)                 │
                 │  S ≤10万   M 10–50万   L 50–500万   XL>500万 │
                 └──────────────────────────────────────────┘
                                   │
   ┌───────────────┬───────────────┼───────────────┬───────────────┐
   ▼               ▼               ▼               ▼               ▼
┌─────────┐   ┌─────────┐   ┌─────────┐   ┌─────────┐   ┌─────────┐
│ L1 后端  │   │ L2 传输  │   │ L3 查看  │   │ L4 编辑  │   │ L5 存储  │
│ 全量diff │   │ 流式收集 │   │ 虚拟渲染 │   │ Worker  │   │ 快照策略 │
│ 分块=备选│   │ 内存优化 │   │ CM只读  │   │ +增量   │   │ IndexedDB│
└─────────┘   └─────────┘   └─────────┘   └─────────┘   └─────────┘
```

- **L1**（后端算法）：**保持全量 diff（实测 100 万字最坏 0.64s）**；分块算法仅作为 >500 万字极端场景的备选路径（§4.1 降级说明）
- **L2**（传输/前端收集）：重点从"diff 进度"转为"**前端收集内存优化**"（边收边 push，消除全量收集内存峰值 ×2）
- **L3**（查看）：只读 CodeMirror 渲染替换 v-html 全量渲染（自带虚拟行）——**最大瓶颈，最高优先级**
- **L4**（编辑）：classifyEdit 移入 Web Worker，UI 不阻塞——**第二大瓶颈**
- **L5**（存储）：草稿迁移 IndexedDB，版本快照 patch 化

各层独立可交付、可回退，最终合并进三期计划（见 §7）。

## 4. 详细方案

### 4.0 L0 文档规模分级（前置，约 0.5 天）

**阈值定义**（按字符数，单文件）：

| 级别 | 范围 | 走哪条路径 | 交互 |
|------|------|-----------|------|
| S | ≤ 10 万 | 现状路径（全量 diff + v-html） | 无提示 |
| M | 10–50 万 | L2 收集优化 + L3 CM 渲染 + L4 Worker | 提示"大文档，对比耗时较长" |
| L | 50–500 万 | 全量 diff（实测 0.64s@100 万）+ L2 + L3 + L4 + L5 | 提示预计耗时与内存占用 |
| XL | > 500 万 | 阻止（或备选分块路径，见 §4.1） | 明确报错"超过 500 万字上限" |

- 前端上传时按 `file.size` 粗估（中文按 ~3 字节/字）给出预警；后端解析后按真实字符数返回 `scale` 字段
- 后端 `_validate_upload` 增加大小上限（默认 500 万字对应字节数），超限返回 BLOCKING 错误（复用现有 `AppError`/`Severity`）
- 与现有 D5 决策衔接：改造完成后上限从 10 万提升到 500 万（预研证明全量 diff 无压力）

**决策点 D-4**：上限阈值取 500 万字是否合适？超限行为用"阻止"还是"警告但允许（可能卡顿）"？

### 4.1 L1 后端：保持全量 diff（分块降级为备选，约 0.5 天）

#### 4.1.0 预研结论（v1.2 重大修订）

实测（`scripts/bench_large.py`，见 §17）：

| 场景（100 万字） | 全量耗时 |
|------------------|----------|
| 5% 行内修改（唯一行语料） | 0.11s |
| 20% 结构性增删+移动（最坏） | **0.64s** |
| 几乎全同 | 0.30s |

**Python diff_match_patch 全量 diff 在百万字量级性能极好**，DMP 内置 half-match 递归分解已把大文本拆小。原方案假设的"O(n²) 退化、分钟级"**不成立**。因此：

- **L1 主路径 = 现有全量 `diff_texts()` 原样保留**，不做分块
- 分块算法（锚点/窗口）**降级为备选**，仅当 `chars > 5_000_000`（500 万字）时按需启用（本方案验收范围 100 万字不触发，具体算法规格保留于 §11 供参考）
- 分块若启用必须走**锚点对齐**（§11.1），严禁窗口硬配对（实测慢 7 倍）；且需块内差异率熔断（块内全差异时回退整块全量 diff，防错位退化——实测简化锚点实现 10 万字结构变化即 22s，必须加此保护）

#### 4.1.1 保留的改动（与分块无关）

- `main.py`：上传大小上限（L0，500 万字）——防内存 DoS，必做
- `diff_engine.py`：无改动（全量 diff 已够快）

#### 4.1.2 备选分块路径（仅 >500 万字触发，默认不启用）

> 保留以下规格作为参考实现。**启用条件：文档字符数 >5,000,000**，且必须同时满足：锚点对齐 + 块内差异率熔断（见 §4.1.0）。

##### 算法：锚点行切分 + 块内字符级 diff

```
输入: orig, modified 两段全文
1. 行级预处理: 按 \n 切行（保留行尾信息），逐行计算 hash（含行内容）
2. 锚点提取: 两边的公共行中，选取长度 ≥ MIN_ANCHOR(20 字符) 且唯一出现 的行作为锚点
   （唯一性避免重复行导致错误对齐；重复文本退化为普通公共行）
3. 区间划分: 用锚点把两文切成 N 个"块区间"（锚点之间为块）
   ┌─锚─┬─块1─┬─锚─┬─块2─┬─锚─┐
4. 块内 diff: 每块内做 diff_match_patch 字符级 diff（Diff_Timeout=0，块小可控）
5. 合并: 锚点段(EQUAL) + 块内 segments 按序拼接 → 输出与现有 diff_texts 相同结构
```

**正确性保证**：锚点行在两边内容完全一致，故块间无跨边界差异；每块独立 diff 与全量 diff 在该区间内等价。拼接结果与全量 diff 在"锚点对齐"的意义上一致。

**熔断保护（必做）**：块内 diff 后若 `差异段字符数 / 块字符数 > 0.7`，判定为锚点错位，**放弃该块的分块结果，改用整块全量 diff**——防止错位导致的 O(n²) 退化（实测简化锚点实现 10 万字结构变化即 22s，而全量仅 0.07s）。

**退化路径**：若锚点稀少（文档几乎全改写），块区间过大 → 触发"窗口分块回退"：按固定窗口（默认 50k 字符）+ 前后 10k 重叠切块，块内 diff 后**重叠区取更长的公共子串对齐**，合并时去除重复。该路径存在理论上的 diff 质量差异（跨块差异可能被拆成两块），需在 UI 无感的前提下接受，并记录为已知限制。**注意：窗口路径实测比全量慢（10 万字 30% 差异 1.37s vs 全量 0.20s），仅作为锚点完全失效时的最后兜底。**

##### 实现要点

- 新模块 `src_backend/diff_engine.py` 内新增 `diff_texts_chunked()`，保留原 `diff_texts()` 供小文档与测试对照
- 行 hash 用 Python 内置 `hash()` 不可靠（进程间不同），用 `zlib.crc32` 或 `hashlib.md5`（截断 8 字节）
- 锚点选择算法用贪心：扫描 modified 行序，维护 orig 中对应位置；参考 diff-match-patch 的 half-match 思路但不依赖其递归
- Unicode：Python 端 `str` 天然 code point，无 surrogate 问题（该坑仅存在于 JS 版）；块边界在 `\n`，不会切碎字符

##### 与后续升级的兼容

- 第三期三方 diff（diff3）升级时，分块边界基于公共锚点，天然是 diff3 的"共同祖先"参照系，冲突检测可逐块进行
- IDML 反向写入（D8）若实现，分块定位到源文档位置更有意义

**决策点 D-2（v1.2 更新）**：100 万字实测全量 0.64s，分块不再必要。备选分块仅保留用于 >500 万字极端场景。是否接受"500 万字内全量、以上走备选分块"？

### 4.2 L2 传输/收集层：前端内存优化（约 0.5–1 天）

v1.2 修订：diff 仅 0.64s，后端"diffing 进度"价值降低；**真正的成本在前端全量收集**——`compare.ts` 先把 2 万+ 个 chunk 全存进 `collectedSegments`，再 `flatMap` 复制一份进 `segments`（百万段内存峰值 ×2，且 2 万次 chunk 解析开销大）。

改造：

1. **边收边 push**：`compare.ts` 的 `onChunk('segments')` 直接 `segments.value.push(...msg.data)`，删除 `collectedSegments` 中间数组与最终 `flatMap`——消除内存峰值 ×2，首块数据立即可用
2. **chunk 粒度调整**：`CHUNK_SIZE` 从"50 段"改为"按字符数"（每 chunk ≤64KB 文本），JSON 序列化/解析次数从 2 万降到约 200 次
3. **渲染提前**：首个 chunk 到达后即触发 `buildContexts()` + 渲染（配合 L3 的 CM 视图），无需等 done
4. **进度**：保留现有 phase 消息即可（`progress` 字段在 chunks 到达时按 `received/totalChunks` 驱动，前端已有逻辑），后端无需额外加工

收益：100 万字对比时首屏可见时间从"diff 全部算完 + 全部收集完"缩短到"首个 chunk 到达"（秒级），内存峰值减半。

### 4.3 L3 查看模式虚拟化：单 CM 实例 + editable 切换（约 2 天）

#### 4.3.1 方案（v1.3 修订：不再为查看单独建 view）

**核心：查看与编辑是同一个 CodeMirror 实例**，通过 `Compartment` 动态切换 `EditorView.editable`：

```
EditorState 配置:
  extensions: [ diffField, userField, searchField, bookmarkField,
                keymap, history(),
                editableCompartment.of(EditorView.editable.of(false))  // 查看态
                ... ]
切换查看↔编辑:  view.dispatch({ effects: editableCompartment.reconfigure(
                  EditorView.editable.of(true|false) ) })
```

收益（相对 v1.1"查看/编辑各建一个 view"）：
- **偏移基准统一**：同一 doc、同一 decoration、同一 `buildDiffSegMap`——v1.1 §15.1"两模式偏移基准不同"的痛点消失，A8 跳转/搜索零适配
- 切换零成本：不重建 view、不丢滚动位置、装饰不重算
- 大文档**默认 Unified 视图**（单文档流，del/mod-old 用删除线 decoration 展示），split 双栏仅保留给小文档（≤10 万字）——规避双栏滚动同步与行号对齐的全部复杂度

#### 4.3.2 落地拆解

1. **抽共享 deco 构建器** `src/render/cmDecos.ts`：`buildDiffDecos(segments, docBasis)` / `buildUserDecos(segments)`，查看/编辑共用（docBasis 参数保留以兼容小文档 split 场景）
2. **diffField 全量改为"查看+编辑双层"**：查看态只显示 diffField（原始差异），编辑态叠加 userField（用户编辑）
3. **UnifiedView.vue 重构** → 只读态 CM（大文档默认）；`SplitView.vue` 保留 v-html 路径给小文档（≤10 万字），或小文档也走 CM 双实例（二期）
4. **退役**：`segmentRenderer.ts` 在 Unified 大文档路径退役；`splitRenderer.ts` 保留给小文档 split
5. **Toolbar/ReportPage 联动**：进入编辑 = `editableCompartment.reconfigure(true)` + 触发 `enterEdit`；退出 = reconfigure(false)

**风险**：Unified 大文档默认意味着"分屏对照"在大文档下不可用（产品取舍，需确认）；删除线样式需与现有 4 色方案对齐——列入 §7 风险表。

### 4.4 L4 编辑模式 Worker 化（阶段一：全量移后台，约 2 天）+ 局部增量（阶段二，约 2–3 天）

#### 4.4.0 两阶段策略（v1.3 修订）

| 阶段 | 内容 | 效果 | 何时做 |
|------|------|------|--------|
| 一 | classifyEdit 全量移 Worker（§12 协议） | UI 零阻塞；高亮延迟 ~1s | P3 先交付（稳定） |
| 二 | Worker 内"变化区间局部重分类"（§4.4.5） | 高亮延迟 <200ms，达成三期验收 | P5 收尾期 |

阶段二与三期 4-11（Decoration 增量）合并实施：worker 输出局部 segment 变更，主线程只局部替换装饰，一石二鸟。

#### 4.4.1 第一优先：classifyEdit 移入 Worker（解决 UI 阻塞）

- 新建 `src/workers/classify.worker.ts`：持有 diff-match-patch 实例，接收 `{ requestId, baseline, edited }`，返回 `{ requestId, segments, dirty }`
- 主线程 `CodeMirrorDiff.vue`：300ms 防抖后，向 worker postMessage；**不等待结果**，UI 保持流畅；worker 返回后 dispatch decoration
- **任务取消/版本号**：worker 端维护递增版本号，收到新任务时丢弃未完成的旧任务（防抖已降频，叠加版本号保证最终一致）
- **降级**：`new Worker()` 失败（老浏览器/严格 CSP）→ 回退主线程执行（现状路径），UI 显示轻量提示
- 消息体：100 万字 baseline+edited 约 4–8MB 结构化克隆，每次编辑一次传输约 10–30ms——**可接受**（相对全量 diff 的秒级阻塞）

#### 4.4.2 store 改造（消除"渲染 = 全量 diff"）

- `editor.ts`：`getEditedSegments()` 不再自己调 `classifyEdit`，改为返回 **worker 最近一次结果缓存**（`lastWorkerSegments`）；`editedStats` / `editedContexts` 由该缓存计算
- worker 结果到达时同步更新缓存 + 版本号（`workerVersion`），`editedContexts` 变为响应式更新

#### 4.4.3 第二优先：Decoration 增量更新（对应三期 4-11）

- `updateListener` 中已有 `update.changes.iterChangedRanges`，据此对 `userField` 做**局部 replace**（`DecorationSet.update({ filter, ... })` 或 `rangeSet.replace`），避免全量 `buildDecoSet`
- 注意 phantom widget（`side:-1`）与周边范围重排的连锁，**复杂度高，列为二期优化**；第一期 Worker 化后 UI 已不阻塞，增量只是进一步降延迟
- `history()` 上限（对应三期 4-10）：无原生 maxDepth 参数，用自定义 StateEffect 定期压缩（超 500 条 undo 记录时丢弃最旧）；或"编辑会话 checkpoint"方案（每 N 次编辑打 patch 快照，undo 超限时整体回 checkpoint）。低优先级，与版本快照改造（L5）共用 patch 能力

#### 4.4.4 大粘贴优化（对应三期 3-12）

- 粘贴 >50k 字符时：绕过 diff 全量（粘贴本身是整段替换），直接按"粘贴区间"构造 user 装饰（粘贴内容全标记为 add，被覆盖区间标 mod-old/new），并提示"大段粘贴已简化标注"

#### 4.4.5 阶段二：变化区间局部重分类（v1.3 新增，正确性论证见下）

**目标**：100 万字每次编辑的 diff 重算从全量 ~1s 降到 <200ms。

**原理**：`baseline` 与 `edited` 的关系中，只有**编辑变化区间附近**的 diff 结果会变；变化区间之外，`baseline` 与"上次 edited"的 diff 关系保持不变（用户没动过那些区域）。因此：

```
Worker 状态:
  lastEdited: string          // 上次分类的 edited 全文
  segIdx: DiffSegIndex        // 上次 segments 的 doc 偏移索引（复用 buildDiffSegMap 思路）
  lastSegments: Segment[]     // 上次结果

收到 classify 请求(baseline, edited):
  1. 若 |edited| 变化占比 >30%（或 lastEdited 为空）→ 回退全量 classifyEdit（熔断）
  2. 否则用 ChangeSet 或 diff_match_patch 计算 edited 相对 lastEdited 的变化区间 [a, b]
  3. 在 segIdx 中定位区间 [a,b] 覆盖的 segment 范围 [i, j]
  4. 取变化区间前后各 Δ(如 5k 字符) 作为"重算窗口"
     - 窗口内文本 = baseline 切片 vs edited 切片（用 segIdx 反查 baseline 对应区间）
     - 窗口外 segments 原样保留
  5. 用窗口内局部 DMP 重算 → 替换 lastSegments[i..j] → 输出局部变更 + 复用部分
```

**正确性依据**：
- 窗口外区域：`baseline[x..y]` 与 `edited[x..y]` 的对应关系未变（用户未触碰），原 segments 仍成立
- 窗口内：局部 DMP 在受限区间内等价于全量 diff 在该区间的结果（锚点式论证：窗口边界落在未变区域）
- 撤销/重做：编辑变化体现在 `edited` 全文，重分类输入仍是完整 `(baseline, edited)`，只是计算上只重算局部——**与 A2"固定基线"语义完全一致，不破坏撤销颜色正确性**

**熔断条件**：变化区间 > 全文 30%、或 segIdx 构建失败、或局部结果与全量校验不一致（debug 断言）→ 回退全量。

**与 Decoration 增量（4-11）合并**：worker 返回 `{ replacedRange: [i, j], newSegments }`，主线程用 `RangeSet.update` 只替换 [i,j] 的装饰，不再全量 `buildDecoSet`。

**决策点 D-3（v1.3 更新）**：阶段一（全量移后台）为必做基础；阶段二（局部增量）是否纳入本轮（建议纳入 P5，与 4-11 合并）。

#### 4.4.6 阶段二实施结果与实测数据（P5，2026-08-04）

**落地形态**：新增 `src/render/incrementalClassify.ts`（纯函数：公共前后缀定位变化区间 + 窗口 ±5000 字符局部 DMP + mergeSegments 去缝重编号 ci）；Worker 端维护 lastEdited/lastSegments 会话状态；主线程 `applyClassifyResult` 支持增量合并（与 store 缓存 merge）。会话同步：主线程清空缓存处（undo 回 baseline / 还原 / 进入编辑 / 草稿恢复）统一发 `reset` 消息，防增量基于过期状态错乱。

**实测数据（30 万字语料，JS diff_match_patch，2026-08-04）**：

| 场景 | 全量耗时 | 增量 | 结论 |
|------|----------|------|------|
| 单处 8→8 字符 | 1.4ms | — | 全量已足够快，增量无收益 |
| 单处 200→200 | 5.7ms | ~3ms | 全量已达标 |
| 单处 2000→2000 | 59ms | 局部窗口 | 增量有收益 |
| 20 处×750（≈5%） | 162ms | 熔断回全量 | 分散多改触发 >30% 熔断 |
| 20 处×1500（≈10%） | 777ms | 熔断回全量 | 最坏场景 Worker 后台执行，UI 不阻塞 |
| 中部插 5 万字 | 0.5ms | — | DMP half-match 极快 |

**重要修订（推翻 v1.2 假设）**：JS DMP 全量对"单处/连续小编辑"极快（30 万字 8→8 仅 1.4ms）——方案文档原假设"百万字每次编辑全量 ~1s"仅对**分散大修改**成立（10% 变化 777ms）。阶段二增量的真实价值收敛为"单处中等修改（2000+ 字符）"的低延迟路径；分散大改由 >30% 熔断回全量（Worker 后台，UI 零阻塞，高亮延迟 ~0.8s 可接受）。装饰层保持全量重建（buildDecoSet/rebuildDiffLayer 为 O(n) 遍历，30 万字 ~20-40ms，相对增量 diff 收益可忽略），4-11 的"局部替换装饰"简化合并入增量 diff 计算层。

**正确性**：增量合并结果与全量 classify 语义等价（doc 文本 + phantom 文本一致；DMP 对局部/全局输入的段粒度划分天然不同，不做逐段断言）——10 项一致性测试 + 3 项性能基准（`src/render/__tests__/incrementalClassify*.spec.ts`）全绿。

**决策点 D-3**：Worker 第一版只做"全量移后台"（简单可靠，高亮延迟 ~1s）还是直接上"增量局部 diff"（复杂，延迟 <200ms）？建议：**先全量移后台**，增量作为二期，用真实用户数据决定是否值得。

### 4.5 L5 持久化：去冗余分层存储（约 1–1.5 天，v1.3 修订）

#### 4.5.0 冗余分析（v1.3 关键优化）

现状 `EditSessionDraft` 同时携带 `editText + baseline + segments` 三个全文级字段（百万字约 6–12MB），且后端 autosave 也全量携带。**baseline 与 segments 都是可重建的冗余**：

| 字段 | 是否冗余 | 来源 |
|------|----------|------|
| `editText` | **必须持久化**（用户编辑全文，唯一不可重建） | — |
| `baseline` | 冗余 | `buildDocText(segments)` 可重建 |
| `segments` | 冗余（本地） | IndexedDB `segments` store 已有（compare store `saveSegments`） |

**去冗余后**：草稿真正需要持久化的只有 `editText`（≤4MB）+ 定位/进度元数据（几 KB）。

#### 4.5.1 分层存储设计（v1.3）

| 层 | 存什么 | 用途 |
|----|--------|------|
| IndexedDB `drafts` store（**新增**） | `{key, editText, cursorPos, scrollPos, lastEditOffset, processedCis, stats, timestamp}` | 主存储：百万字草稿完整恢复 |
| IndexedDB `segments` store（**现有**） | 对比 segments chunks | 恢复时免重跑对比（已有 `saveSegments`） |
| localStorage（**现有 key 前缀 `cmp_edit_`**） | 索引摘要 `{key, fileAName, fileBName, timestamp, processedCount, hasSegments}` | 首页草稿列表展示（几 KB，替代原全文草稿） |
| 后端 autosave | `editText + 定位字段 + stats`（**去掉 segments/baseline**） | 跨设备兜底，payload 缩至 ~1/10 |

**恢复链路（降级顺序）**：
1. IndexedDB `drafts` 有完整 `editText` + `segments` store 有数据 → 直接恢复
2. 后端 autosave 有 `editText`，本地 segments store 有 → 后端文本 + 本地 segments
3. 只有 localStorage 摘要 → 提示用户重传文件重跑对比

- 现有 `storage.saveEditDraft` 的剥离降级逻辑随迁移移除（IndexedDB 无 5MB 配额限制）
- `enterEdit` 恢复逻辑（editor.ts）同步改为按上述链路读

#### 4.5.2 版本快照 patch 化（D-5，后置）

- 现状（已确认）：`version_manager.py` 存 `file_a_content` + `file_b_content` 全量文本，JSON 上限 10 个；100 万字单版本约 4MB、全量 40MB
- 改造（后置）：复用已有 `make_patches(baseline, current)` / `apply_patches`——**快照 = 基线 hash + patch 序列**，恢复时逐条 apply
- 收益：kb 级 patch 替代 MB 级全量

#### 4.5.3 autosave 频率与体积

- 2s 防抖对百万字后端写盘过频：保存间隔提升到"防抖 2s + 空闲 5s 合并"，或体积阈值触发（编辑量 >1MB 才写）
- autosave payload 去掉 segments/baseline 后（§4.5.1），序列化与网络成本大幅下降，后端文件保持明文 JSON 按 key 分片

**决策点 D-5 / D-6（v1.3 更新）**：D-6 已确认按 §4.5.1 分层去冗余方案执行；D-5 版本快照 patch 化仍建议后置到三期。

## 5. 多角度评估

### 5.1 性能

| 指标 | 现状（100 万字） | 改造后 | 达成手段 |
|------|----------------|--------|----------|
| 后端 diff 耗时 | **0.11–0.64s（实测，非瓶颈）** | 不变（全量） | 无需改造（v1.2） |
| 首屏可见时间 | 等全部收集完 | 首 chunk 到达即渲染（秒级） | L2 边收边 push + 提前渲染 |
| 前端收集内存峰值 | 全量收集 ×2 | 减半 | L2 去 collectedSegments |
| 查看模式 DOM 节点 | 数十万 | ~可视行数（恒定） | L3 CM 虚拟行 |
| 编辑 UI 阻塞 | 每次编辑秒级 | 0（后台 worker） | L4 Worker |
| 编辑重算延迟 | 秒级 | <200ms 目标 | L4 Worker +（二期）增量 |
| 草稿保存 | 超配额失败 | 正常 | L5 IndexedDB |

### 5.2 正确性

- **分块等价性**：锚点行保证块边界内容一致，块内独立 diff 等价于全量 diff（该区间内）；用 property test 对随机语料验证（含增删改、整段重排、Unicode）——见 §5.6
- **Unicode**：后端 Python str 天然 code point 安全；前端保持 `Array.from` 处理 surrogate（记忆：JS DMP 对 surrogate pair 错位）；分块在 `\n` 边界，不切碎字符
- **窗口回退的已知限制**：差异极大文档（锚点 <阈值）走固定窗口，跨窗口差异可能被拆分——记录为已知限制，仅影响极端场景
- **行尾**：`normalizeLineEndings` 已统一 LF，分块在行边界，无 \r 干扰

### 5.3 架构与可维护性

- 查看/编辑共用 CM 渲染管线 → 单一渲染路径，删除 v-html 双路径，代码量净减
- L1 分块作为 `diff_engine` 的新函数保留旧函数 → 小文档路径不受影响，回归风险隔离
- Worker 协议（requestId/version）简洁，可测试（worker 逻辑抽为纯函数供 vitest 直接测）
- 决策影响范围：L3 影响面最大（双视图组件重写 + 样式对齐），应独立一期、独立回退

### 5.4 UX

- 对比阶段：真实进度（块级）+ 边算边显示，消除"进度条卡 50%"的观感
- 编辑阶段：无卡顿；worker 计算中如需提示，侧边栏轻量"分析中…"（<200ms 目标下可不显示）
- 规模预警：M 级提示耗时，XL 级阻止并说明原因（替代当前无声卡死）
- 降级透明：Worker 失败自动回主线程，用户无感（仅控制台提示）

### 5.5 安全

- 退役 v-html 渲染路径 → 移除一处潜在 XSS 面（现有 esc() 已转义，但 CM 渲染本身无 innerHTML 注入）
- 上传大小限制（L0）→ 防内存 DoS（200MB+ 文件直接拒绝）
- Worker 仅本地计算，无网络面，无新增攻击面
- 后端分块不引入任何脚本执行；patch 快照 apply 用 DMP 库既有实现（已用于导出/恢复路径）

### 5.6 测试与性能基准

新增测试（并入三期 E 组）：

| 类型 | 用例 |
|------|------|
| 后端单元 | 分块 diff 与全量 diff 在随机语料上输出一致（property test，≥100 组：增删改混合/整段重排/空文件/纯差异/Unicode CJK-Ext） |
| 后端单元 | 锚点稀少退化路径触发正确、窗口重叠合并正确 |
| 前端单元 | worker 协议（requestId 乱序、版本号丢弃旧任务）；store 消费 worker 缓存；deco 构建器在只读/编辑两模式输出一致 |
| 前端单元 | 大粘贴简化标注逻辑 |
| 性能基准 | fixture 生成 10 万/50 万/100 万字合成文档：diff 耗时、首帧、编辑重算延迟（CI 记录，超阈值标红） |

  - 4-9（DMP Worker）→ 由 L4 完成

## 11. L1 分块算法详细规格

### 11.1 锚点提取（贪心，O(n₁+n₂)）

```
输入: lines_orig[], lines_mod[]（已按 \n 切分，含行尾信息）
输出: anchors = [(idx_orig, idx_mod)]，升序、互不交叉

1. 计算每行 hash（crc32(行内容)，含换行符区分位置）
2. 建 orig 侧 index: hash -> [行号]（仅收录长度 ≥ MIN_ANCHOR=20 的行）
3. 扫描 modified 行 i=0..n：
   a. 行 hash 在 orig index 中且该 orig 行号 > last_orig_pos 且唯一出现（count==1）
      → 记为候选锚点
   b. 候选锚点与上一锚点之间，若 orig 侧跨度 < 40 行且 modified 侧跨度 < 40 行
      → 直接收下（密锚点，块小）
   c. 否则计算中间地带是否有更大的唯一公共行；没有则收下当前候选
4. 首尾处理：文档最前/最后若没有锚点，分别从首行/末行找最近公共行补齐
   （保证所有文本都被纳入某个块区间）
```

**不变量**：任意两个相邻锚点 `(a, a')` 之间，orig 与 modified 的区间长度差 = 该块内的净增删量；锚点行本身为 EQUAL 段。

### 11.2 块区间与全局 ci 编号

- 块 k 覆盖 `orig[a_k+1 .. a_{k+1}-1]` 与 `mod[a'_k+1 .. a'_{k+1}-1]`（锚点之间）
- 块内 `diff_match_patch` 字符级 diff → 局部 segments（局部 ci 从 1 起）
- **全局 ci 编号**：块 k 的起始 ci = `base_ci[k] = Σ(前 k 块内 change 数)`。输出时 `ci = base_ci[k] + 局部 ci`——保证与现有全量 diff 的 `ChangeContext.index` 全文档连续语义一致（Sidebar 依赖）
- 锚点段输出为 `{text, operation:'none', origin:'original'}`（无 ci，与现状一致）

### 11.3 窗口回退（锚点不足时）

触发条件：`锚点间隔区间中，任一区间 orig 或 modified 跨度 > MAX_BLOCK_CHARS(50k)` 且 `锚点总数 < 全文行数 10%`。

```
1. 按 50k 字符固定窗口切分（优先在 \n 边界对齐）
2. 相邻窗口重叠 10k 字符（重叠区取完整行）
3. 每窗口独立 diff → 局部 segments
4. 合并：重叠区两侧的 diff 结果，若都含 EQUAL 子串且一致 → 取其一保留；
   若一侧是纯变更另一侧是 EQUAL → 保留变更侧（变更优先）
5. 输出时重叠区只保留一次；全局 ci 同 §11.2
```

已知限制：跨窗口的单一变更可能被拆成两段显示（如一个 60k 字符的连续改写会被切成 2 块）。记录为文档已知限制，锚点充足时不会触发。

### 11.4 复杂度预估（100 万字，约 33k 行，30 字/行）

| 步骤 | 复杂度 | 预估耗时 |
|------|--------|----------|
| 行 hash + 锚点提取 | O(n) | <1s |
| 块内字符 diff（假设 47 块 × ~20k 字符） | 47 × O(20k²) 局部 | 5–20s（Python DMP，C 核心略快） |
| cleanupSemantic + 拼接 | O(n) | 1–3s |
| **合计** | 近线性 | **≤30s 目标** |

若 Python `diff_match_patch` 纯 Python 实现过慢，备选：块内用 `difflib.SequenceMatcher(autojunk=False)` 先行、仅对命中差异的行做字符级 DMP 精化（混合策略，列入性能基准验证项）。

## 12. L4 Worker 协议完整定义

### 12.1 消息 schema

```ts
// 主线程 → Worker
interface WorkerRequest {
  type: 'classify';
  requestId: number;      // 单调递增
  version: number;        // 全局编辑版本号，旧任务丢弃依据
  baseline: string;
  edited: string;
}
// Worker → 主线程
interface WorkerResponse {
  type: 'result' | 'error' | 'ready';
  requestId?: number;
  version?: number;
  dirty?: boolean;
  segments?: Segment[];   // 仅 dirty=true 时非空
  message?: string;       // error 时
}
```

### 12.2 Worker 端状态机

```
idle ──收到 classify──> computing
computing ──完成──> postMessage(result) ──> idle
computing ──收到新 classify（version 更大）──> 丢弃当前计算（中断标记）──> computing(新)
computing ──出错──> postMessage(error) ──> idle
```

- DMP 是同步计算，无法真正"取消"——用**版本号丢弃**：主线程只接受 `version === 当前版本` 的响应；worker 端在计算前检查待处理队列，若已有更新请求则跳过本次发送（省一次 postMessage 与主线程丢弃开销）
- 主线程同一时刻只发一个 in-flight 请求；防抖 300ms 保证不会洪泛

### 12.3 主线程时序

```
用户输入 ──> updateListener（仅记 cursor/lastEdit，不阻塞）
    └─ 300ms 防抖 ──> editText = doc.toString()
        └─ postMessage({version: v+1, baseline, edited})  // 不等待
worker 返回 ──> version 匹配？── 是 ──> setUserDecos + rebuildDiffLayer + store 缓存更新
                        └─ 否 ──> 丢弃（旧任务结果）
```

### 12.4 降级链路

| 触发 | 行为 |
|------|------|
| `new Worker()` 抛异常 / 构造失败 | 回退主线程 `classifyEdit`（现状路径），console.warn 一次 |
| worker 连续 2 次 error 或 10s 无响应 | 置 `workerBroken=true`，永久回退主线程 |
| worker 结果与 doc 当前状态不符（防抖窗口内又有输入） | 版本号不匹配自动丢弃，无感知 |

### 12.5 store 缓存改造（消除"渲染 = 全量 diff"）

```ts
// editor.ts
const workerSegments = ref<Segment[] | null>(null);   // 最近一次 worker 结果
const workerVersion = ref(0);

getEditedSegments(): Segment[] {
  // 不再调 classifyEdit；返回 worker 缓存（未计算时返回空）
  return workerSegments.value ?? [];
}
// worker 回调里：workerVersion.value = version; workerSegments.value = segments;
// flushEditsSync（导出用）仍需同步：内部保留主线程 classifyEdit 兜底，仅导出路径调用
```

## 17. 性能预研结果（v1.2，实测数据）

> 工具：`scripts/bench_large.py`（已入库，可复跑）
> 环境：Python 3.13.12 venv（compare-test）+ 纯 Python diff_match_patch（已确认无 C 加速）
> 语料：`fixtures/275导出.txt`（6791 字符）循环拼接 + 每行唯一编号（`〔k〕`，防 DMP 重复文本优化作弊）；变异算子：light=行内改字，struct=整行增删+移动（最坏场景）

### 17.1 数据表

| 规模 | 变异 | 全量 diff | 窗口分块 | 锚点分块 |
|------|------|-----------|----------|----------|
| 10 万 | 5% light | ~0.01s | ~0.01s | ~0.01s |
| 10 万 | 30% light | **0.20s** | 1.37s（慢 7×） | 0.19s |
| 10 万 | 20% struct | **0.07s** | — | 21.97s（错位退化） |
| 100 万 | 5% light | **0.11s** | 0.06s | 0.02s |
| 100 万 | 20% struct | **0.64s** | — | >300s（已终止） |
| 100 万 | 几乎全同（纯字符） | 0.30s | — | — |

### 17.2 结论

1. **Python DMP 全量 diff 在百万字量级性能极好**（最坏 0.64s），其内置 half-match 递归分解已自带"分块"能力——原方案"O(n²) 退化、分钟级"假设不成立
2. **分块方案有害**：
   - 窗口硬配对：块间不连续对齐，比全量慢 7 倍（10 万 30% 场景）
   - 简化锚点分块：结构性变化（增删移动）导致锚点错位 → 块内大段全差异 → O(n²) 退化（10 万 struct 22s；100 万 >300s 被终止，而全量仅 0.64s）
3. **若未来 >500 万字启用分块**，必须：锚点对齐（严禁窗口硬配对）+ 块内差异率熔断（>70% 差异即回退整块全量）——否则不如直接全量
4. **真正的性能瓶颈在前端**：v-html 全量 DOM（L3）与编辑模式每次全量 classifyEdit 阻塞 UI（L4），本方案优先级随之调整：P1 后端从 2–3d 缩减到 0.5–1d，重心移至 P2/P3

### 17.3 对验收标准的影响

| 原验收锚点 | 修订 |
|-----------|------|
| "100 万字对比总耗时 <60s" | **<10s 可达成**（diff 0.64s + 传输/渲染为主） |
| "首屏可见 <5s" | 维持，靠 L2 边收边渲染 |
| "后端 diff ≤30s" | **无需该指标**（实测 0.64s），改为前端渲染/编辑指标 |
| 编辑重算 <200ms | 维持，靠 L4 Worker（JS DMP 与 Python 同源，百万字主线程全量约 1s 级，必须 Worker 化） |
