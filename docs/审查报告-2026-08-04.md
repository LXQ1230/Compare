## 三、P1 严重问题详情

### P1-1 版本历史功能整体损坏 🔴

**现状**：版本历史是 3 个独立缺陷叠加，导致功能完全不可用。

**缺陷 a — 无 UI 入口**
- `ReportPage.vue:33` 定义 `showVersions = ref(false)`，全项目搜索确认**没有任何组件/按钮把它置为 true**。
- `<VersionHistory v-if="showVersions" />` 永远不渲染 → 对话框无法打开。
- 复现：报告页工具栏有"导出"但**没有"版本历史"按钮**，任何操作都无法打开版本界面。

**缺陷 b — 保存内容为空**
- `VersionHistory.vue:10`：`versionStore.saveVersion(label || ..., '', '', {})` —— `fileAContent`/`fileBContent` 传空字符串，`stats` 传空对象。
- 后端 `version_manager.py:48` 对空内容生成 patch（或全量空串）。
- 动态验证：API 保存空内容版本 → `restore` 返回 `file_a_content=''`（空文档）。**保存的版本恢复出来是空白**。

**缺陷 c — 恢复结果不应用**
- `VersionHistory.vue:22`：`@click="versionStore.restoreVersion(v.id)"` —— 只调用不处理返回值。
- `version.ts:42-51` `restoreVersion` 返回 `result.version`，但没有任何代码把内容应用到 segments/meta/编辑器。
- 复现：即使打开了版本对话框，点击"恢复"后界面无任何变化。

**修复建议**（方案）：
1. 工具栏增加"📚 版本历史"按钮 → `showVersions = true`。
2. `saveVersion` 改为从 `compareStore` 传入真实内容：`saveVersion(label, buildDocText(fileA 侧段), buildDocText(fileB 侧段), compareStore.stats)`（需按现有语义确认 A/B 侧文本来源，可参照 `mergeLayers` 的投影逻辑）。
3. `restoreVersion` 成功后，将返回的 `file_a_content`/`file_b_content` 应用到视图（重新构建 segments 或提示跳转编辑模式）。

### P1-2 `/api/compare` 先读后查（内存 DoS）🔴

**位置**：`src_backend/main.py:193-211`

**缺陷**：
```python
tmp_a.write(await fileA.read())   # ← 整个文件先读入内存
...
size_a = tmp_a.tell()             # ← 读完才检查大小
if size_a > COMPARE_MAX_BYTES:    # ← 超限时内存已被撑满
```
- `await fileA.read()` 将完整上传内容读入进程内存。15MB 上限时单请求峰值 ≥15MB；若通过环境变量调大上限（如 500MB），单请求可占 500MB+ 内存。
- 真正的风险点：**检查发生在完整接收之后**，攻击者可以持续流式上传任意大小文件，服务器无中途拦截。
- 动态验证：15MB+1KB 文件 0.1s 内被拒绝（413），证明"读完后才拦"。

**修复建议**：
1. 读取时分块并累计计数，超限立即中断：
```python
CHUNK = 256 * 1024
total = 0
while True:
    chunk = await fileA.read(CHUNK)
    if not chunk: break
    total += len(chunk)
    if total > COMPARE_MAX_BYTES:
        raise AppError(..., status_code=413)
    tmp_a.write(chunk)
```
2. 或在依赖层限制请求体（如 nginx `client_max_body_size`、uvicorn `--limit-max-request-size` 等）。

> 注：本工具面向本地单用户，实际危害有限，但作为防御性修复成本极低、收益明确，建议优先处理。

## 四、P2 中等问题详情

### P2-1 草稿恢复的会话硬刷新后丢失 🟠（动态确认）

**复现**：首页点"未完成的编辑"→ 继续编辑（URL `/report/a5414820`）→ **刷新页面** → 被踢回首页。

**根因**：
- `compare.ts:180-199` `restoreFromDraft` 用 `draft.timestamp`（草稿保存时间）计算新 sessionId，但**未调用 `storage.saveMeta()` 持久化**。
- `ReportPage.vue:41-73` 硬刷新恢复依赖 localStorage `cmp_meta`（其中 timestamp 还是**首次对比**的时间）→ 计算的 sessionId 与 URL 不符 → `router.replace('/')`。
- 数据未丢（草稿仍在 IndexedDB/localStorage），但用户被迫重新点击恢复，编辑定位状态需要重新走一遍。

**修复建议**：`restoreFromDraft` 中同步 `storage.saveMeta(meta.value)`（或持久化草稿摘要时连带更新 cmp_meta）。

---

### P2-2 编辑模式搜索 ▲▼ 导航失效 🟠（动态确认）

**复现**：编辑模式 → Ctrl+F 搜索"如來" → 高亮 2 处、计数 "1/2" 正常 → 点 ▼ → 计数变 "2/2" 但**编辑器不滚动**（scrollTop 恒 0）。

**根因**：`search.ts:71-103` `scrollToActiveMatch` 走 DOM 锚点：`getElementById('ci-${ci}')` → 再找 `.seg-search-hl`。**编辑模式下 v-html 视图被 CodeMirror 替代，DOM 中不存在 `ci-N` 元素**（动态验证 `ciAnchors: 0`）→ `if (!el) return` 静默返回。

**修复建议**：编辑模式下改为 CM 通道（类似 `__cmScrollToCi`），或利用 CM 搜索高亮位置直接 `view.dispatch(scrollIntoView)`。查看态小文档不受影响。

---

### P2-3 大文档查看态侧边栏点击无跳转 🟠（动态确认）

**复现**：上传 88 万字节大文档（scale M）→ 查看态 → 点击侧边栏变更项 → 无任何滚动。**但直接调用 `host.__cmScrollToCi(10)` 滚动正常**（scrollTop 0 → 15145）——证明 CM 通道可用，是 Sidebar 没走。

**根因**：`Sidebar.vue:38` 只判断 `editorStore.isEditing && host?.__cmScrollToCi`，**缺少 `isLargeDoc` 分支**。大文档查看态 `isEditing=false` → 走 DOM 分支 `getElementById('ci-${ci}')` → CM 渲染无该 id → 静默失败。`ReportPage.vue:126` 的 `scrollToContext` 正确处理了 `isLargeDoc`，但**侧边栏用的是自己实现的 `scrollTo`，两处逻辑不一致**。

**修复建议**：`Sidebar.vue:38` 条件改为 `(editorStore.isEditing || isLargeDoc) && host?.__cmScrollToCi`。

---

### P2-4 编辑态侧边栏跳转偏移可能错位 🟠（静态确认）

**根因**：`CodeMirrorDiff.vue:716-740` `buildOffsetMap` 仅在进入编辑/查看态时构建一次（基于 `editSegments` 的**编辑前**偏移）。用户在文档中插入/删除文本后，`segOffsets` 记录的偏移与当前 doc 不再对应 → `scrollToCi` 跳到错误位置（偏前/偏后）。编辑态 Sidebar 的 ci 序列还来自 Worker 分类结果（`editedContexts`，新 ci 编号），与 `segOffsets`（原始 ci）**语义不同源**，进一步放大错位。

**修复建议**：
1. 编辑态跳转改用"当前 doc 中查找目标变更文本"的方式（如按 `editedContexts[ci].highlight` 在当前 doc 中定位），或
2. 编辑过程中用增量方式维护 segOffsets（利用 `incrementalClassify` 的窗口信息），或
3. 至少用 `changes` 反向映射：dispatch 跳转时把存储偏移通过用户编辑的 ChangeSet 换算成当前偏移。

---

### P2-5 「从头开始」不清理已存草稿 🟠（静态确认）

**根因**：`editor.ts:294-304` `resetToOriginal` 仅重置内存状态（`resetToken++` 触发 CodeMirrorDiff 重写 doc），**不调用 `storage.clearEditDraft` / `api.autosave delete`**（对比 `discardDraft` 有清理）。已保存的旧草稿残留，用户下次进入编辑模式时**再次弹出"检测到上次编辑未完成"**，与用户"从头开始"的意图冲突。

**修复建议**：`resetToOriginal` 中同步清理 `draftKey` 对应的草稿（双写删除，参照 `discardDraft`）。

---

### P2-6 压缩 undo 历史后第一次真实编辑的 classify 被跳过 🟠（静态确认）

**位置**：`CodeMirrorDiff.vue:583-588`

**根因**：`compressHistory()` 设置 `suppressClassifyNext = true` 后 `v.setState(newState)`。但 `setState` 相同 doc 产生的 update `docChanged === false`，**在第 583 行 `if (!update.docChanged) return` 提前返回**，标志不会被消费；`compressHistory` 结束也未重置。下一次**真实编辑**触发 `docChanged=true` 的 update 时，第 585 行消费标志并 `return` → **该次编辑的分类装饰被整体跳过**（classifyTimer 也不会设置），UI 装饰停滞直到用户再次输入。

**触发条件**：撤销操作超过 500 次（`undoDepth > MAX_UNDO_DEPTH`）触发压缩——低频但后果是编辑反馈丢失。

**修复建议**：压缩重建后显式消费标志（如在 `compressHistory` 内 `setState` 后 `queueMicrotask`/`nextTick` 重置，或改为比对 doc fingerprint 而非布尔标志）。

---

### P2-7 localStorage 草稿摘要与 IndexedDB 主体不一致 🟠（静态确认）

**根因**：`storage.ts:88-158` `saveEditDraft` 先写 IndexedDB 再写 localStorage 摘要；`clearEditDraft` 先删 IndexedDB 再删摘要。任一步失败（配额满、IDB 异常）都会造成：
- 摘要存在但 IDB 主体缺失 → 首页显示草稿，点击恢复报"正文缺失"；
- 或 IDB 有主体但摘要缺失 → 首页不显示，草稿"看不见"。
`listEditDrafts` 的 `processedCis` 还是从摘要 `processedCount` 近似重建的 `[1..count]`，与真实集合可能不符（用户跳号标记时展示错误）。

**修复建议**：写/删顺序改为"先摘要后主体/先主体后摘要"并加失败回滚；列表加载时校验摘要与 IDB 一致性。

---

### P2-8 protectAstral 占位符冲突 🟠（静态确认）

**位置**：`unicode.ts:66-94`

**根因**：私有区 U+E000–U+F8FF 仅 6400 个码位。当单次 diff 的两个输入合计包含超过 6400 个**不同**的非 BMP 字符（如大型 emoji 文档、罕见汉字扩展区），`for` 循环找不到空闲码位，`ph` 保持 `\uE000`，且 `map.set('\uE000', ch)` **覆盖前一个映射** → 多个不同字符映射到同一占位符 → `restoreAstral` 还原错乱，diff 结果文本损坏。

**修复建议**：用字符串拼接式替代方案（如将 astral 字符替换为带编号的 ASCII 标记序列），或检测溢出后回退到无保护的全量 diff（宁可 diff 粒度粗糙也不损坏文本）。

- `COMPARE_MAX_BYTES` 默认 15MB 上限存在，但如 P1-2 所述"先读后查"削弱了它的防御意义。
