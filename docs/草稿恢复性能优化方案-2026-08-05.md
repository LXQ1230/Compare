# 草稿恢复性能优化方案（方案 B：userSegments 免重算）

> 2026-08-05 · 背景：70 万字测试文档点击"继续编辑"需等待 5–20 秒才出页面。
> 根因：恢复草稿时 `CodeMirrorDiff.ensureEditor` 在**主线程同步**执行 `classifyEdit`（diff-match-patch
> 全量 diff + 标点归因管线，`Diff_Timeout=0` 无超时），期间页面白屏。

## 1. 结论

- **免重算优于异步化**：方案 A（worker 异步）只是把卡顿挪到后台，装饰后补存在偏移风险；方案 B 在保存时缓存"用户编辑分类结果"（`userSegments`），恢复时直接复用，**从根上消除 diff 计算**。
- 目标：70 万字草稿恢复出页面 **≤1 秒**（当前 5–20 秒）；保存路径零新增阻塞。

## 2. 耗时构成（70 万字，现状）

| 环节 | 耗时 | 是否消除 |
|---|---|---|
| DMP 全量 diff（主线程同步，无超时） | 5–20 s | ✅ 免重算消除 |
| 标点归因管线 L1→L2→L3→W→merge | 0.5–1 s | ✅ 免重算消除 |
| IDB 读 draft + segments（串行） | 0.3 s | 并行化 → ~0.2 s |
| 装饰重建 ×3 + CM 首屏 | 0.5 s | 保留（必要） |

## 3. 设计要点

### 3.1 核心洞察

`saveDraft` 触发时（防抖 2s / exitEdit / 保存按钮），`editorStore.workerSegments`（最近一次 classify 的完整结果）**当时就在内存里**。当前丢掉了这个字段，恢复才被迫重算。把它随草稿持久化即可。

### 3.2 类型扩展（`src/types/index.ts`）

```ts
export interface EditSessionDraft {
  // ...现有字段
  /** 保存时的基线快照（不再剥离；校验 userSegments 配套关系） */
  baseline: string
  /** 用户编辑分类结果（方案 B：恢复免重算 DMP diff；undefined=缓存未就绪/旧草稿） */
  userSegments?: Segment[]
}
```

### 3.3 存储策略

| 存储 | 内容 | 变化 |
|---|---|---|
| IDB `drafts` store（主体） | editText + **baseline 快照（恢复保留）** + **userSegments** + 定位字段 | `saveEditDraft` 不再剥离 baseline；新增 userSegments |
| localStorage（摘要） | 索引字段（无正文） | 不变（userSegments 太大，严禁入 localStorage） |
| 后端 autosave | editText/定位字段（现状） | **不存 userSegments/baseline**（JSON 明文膨胀），IDB 缺失时回退 worker 异步 |

- IDB `drafts` 为 `{key, value}` 自由结构，**无需 schema 升级**（DB_VERSION=2 不动）。
- 体积评估：70 万字 → editText ~2MB + baseline ~2MB + userSegments ~2–5MB（structured clone 免 JSON 序列化），单记录 ~6–10MB，IDB 可容纳。

### 3.4 保存路径（`src/stores/editor.ts` saveDraft）

关键：**只存"与当前 editText 配套"的缓存**，防止存了过期结果。

```ts
// store 新增：最近一次成功 classify 的编辑文本快照
const workerEditedText = ref("")
function setWorkerResult(version: number, segments: Segment[], editedText = editText.value): void {
  workerVersion.value = version
  workerSegments.value = segments
  workerEditedText.value = editedText
}
```

```ts
// saveDraft 内：
const cacheFresh = workerSegments.value !== null && workerEditedText.value === editText.value
const draft: EditSessionDraft = {
  ...,
  baseline: originalBaseline.value,          // 保留快照（原实现已有，storage 层不再剥离）
  userSegments: cacheFresh ? workerSegments.value! : undefined,
}
```

时序说明：编辑 → 300ms 防抖 classify（worker 异步，70 万字全量 ~1–5s）→ 2s 防抖保存。**worker 可能未返回**，此时 `workerSegments` 为 null/旧值 → 不存 userSegments，恢复回退异步重算（页面仍 <1s 出）。保存永不阻塞。

### 3.5 恢复路径（`CodeMirrorDiff.vue` ensureEditor 690–723 行替换）

```ts
if (editorStore.hasEdits && editorStore.editText && editorStore.editText !== baseline) {
  const cachedUser = editorStore.draftUserSegments ?? null

  if (cachedUser && cachedUser.length > 0) {
    // 主路径（免重算）：直接用缓存分类结果
    view.dispatch({ effects: setUserDecos.of(buildDecoSet(cachedUser)) })
    rebuildDiffLayer(view, cachedUser)
    editorStore.setWorkerResult(++editVersion, cachedUser, editorStore.editText)
  } else {
    // 回退路径（旧草稿/缓存缺失）：worker 异步重算，UI 零阻塞
    const version = ++editVersion
    classifyInWorker(baseline, editorStore.editText, version, (resp) => {
      if (!view) return
      if (resp === null || resp.type === 'error') {
        // worker 不可用 → 主线程兜底（一次性）
        applyClassifyResult(classifyEdit(baseline, editorStore.editText), version)
        return
      }
      if (resp.version !== version) return
      applyClassifyResult({
        dirty: resp.dirty ?? false,
        segments: resp.segments ?? null,
      }, version)
    })
  }
  // 光标/滚动/书签恢复照旧（不等 worker），立即执行
}
```

- worker 首次 classify 时内部 session=null → 走全量路径返回完整 segments（已验证 `classify.worker.ts` 逻辑）。
- `watch` 里 `resetWorkerSession()` 在 ensureEditor 之后执行：classify 先投递、reset 后投递，worker 端先全量算（正确）再清 session（下次编辑回退全量一次，可接受，正确性优先）。

### 3.6 store 传递（`editor.ts` / `SelectPage.vue`）

```ts
// store 新增临时 ref：本次会话待用的草稿 userSegments
const draftUserSegments = ref<Segment[] | null>(null)

// resumeFromDraft / enterEdit（acceptDraft 前）：携带
draftUserSegments.value = draft.userSegments ?? null
```

- `resumeDraft`（SelectPage）：IDB `loadEditDraft` 已带出 userSegments → `resumeFromDraft(full)` 自动传递。
- 重传文件 → 编辑 → 弹窗 → `acceptDraft`：`pendingDraft.userSegments` 同样带出。
- baseline 快照：`loadEditDraft` 不再强制 baseline=''；`resumeFromDraft` 的 `draft.baseline || 重建` 逻辑天然兼容新老草稿。

### 3.7 一致性校验

- `userSegments` 基于保存时的 `originalBaseline` 分类。保存的 baseline 快照逐字节复用 → 天然一致，**无需指纹校验**。
- 唯一出口：`draft.baseline` 为空（旧草稿）→ `userSegments` 必然也缺失（旧草稿无此字段）→ 走回退路径。二者同源同失，无错位可能。

## 4. 防御性修补（顺带，独立提交）

1. **`diffSafely` 的 `Diff_Timeout=0` → 3s 有界**：任何漏网路径（导出 flush、worker 不可用降级主线程）不再无限卡。DMP 超时返回半结果，质量下降但可接受（仅兜底路径）。
2. **`resumeDraft` IDB 串行 → 并行**：`Promise.all([loadEditDraft, getAll('segments')])`，省 ~0.1–0.2s。
3. **独立问题（不在本轮）**：编辑态 `flushEditsSync`（导出/侧边栏跳转）的主线程同步全量 classify，70 万字同样会卡——建议后续单独一期（导出走 worker 或增量 flush）。

## 5. 测试计划

| 级别 | 用例 |
|---|---|
| 单测 `storage-drafts.spec.ts` | saveEditDraft round-trip 保留 baseline + userSegments；localStorage 摘要不含正文 |
| 单测 `compare-restore.spec.ts` | saveDraft 缓存新鲜/不新鲜两分支；resumeFromDraft 设置 draftUserSegments |

| 前端 e2e（agent-browser，70 万字） | 编辑 3 处 → 等 2s 防抖保存 → 首页恢复 → 出页面 ≤1s + 装饰正确（截图比对） |
| 回归 | 老草稿（手工删除 userSegments 字段）恢复仍可用（worker 回退）；undo 回 baseline 保存不产生空草稿 |

## 6. 验收标准

- 70 万字：点击"继续编辑"→ 出页面 ≤1s（含 IDB 读 + 装饰重建 + CM 首屏）。
- 回退路径（旧草稿）：首帧 <500ms，worker 返回后装饰就位，期间可滚动不卡。
- 保存路径无新增主线程阻塞（saveDraft 不触发 flush）。
- 后端 autosave 体积不增长。

## 7. 风险与回退

- **userSegments 体积**：~2–5MB 进 IDB 单记录，put/get 增加几十~几百 ms（可接受）；不入 localStorage（已约束）。
- **过期缓存**：`workerEditedText === editText` 新鲜度校验兜底，存不了就回退，无错位。
- **回退**：删除 `userSegments` 字段即回老路径（worker 异步），无数据损坏；IDB 记录可整体删除草稿重建。

## 9. 实施结果与实测（2026-08-05 完成）

### 9.1 已完成
- 方案 B 全链路落地 + 防御补丁（§3/§4 全部）
- 单测：前端 147 全过（新增 editor-draft-cache 11 例 + storage round-trip 2 例）；vue-tsc 0 错误；vite build 通过
- e2e（70 万字 perfA/perfB，agent-browser）：编辑→保存→恢复全链路验证

### 9.2 实测数据（70 万字）
| 指标 | 修复前 | 修复后 |
|---|---|---|
| 点击"继续编辑"→ 编辑态 CM 出现 | 5–20s（主线程 DMP diff 无限阻塞） | **3.8–3.9s**（稳定复现，maxGap≈3.9s 单次同步阻塞） |
| 草稿 IDB 落盘 | ✅（基线 714808 + userSegments 2 段） | — |
| 用户装饰恢复 | 免重算主路径（buildDecoSet 缓存），非 worker 回退 | — |

### 9.3 打点分解（恢复 3.9s）
```
ensureEditor: mapDiffSegs 91ms / bToAMap 3ms / diffSegMap 2.5ms / stateCreate 1.3ms
              viewCreate 1828ms ← new EditorView（浏览器强制同步布局，绝对大头）
              decoDiff 6.6ms / cursorRestore 5.4ms
resumeDraft: idbRead 27ms / restore(buildContexts) 91ms / resume 76ms / push 0.1ms
```
CPU profile（traceEvents）：`Blink.ForcedStyleAndLayout 1749ms` + `Layout 1390ms` —— viewCreate 的 1.8s 是 CM 对 70 万字 doc 初始化触发的浏览器强制布局（**查看态同款成本**，非恢复路径独有）。

### 9.4 实施中发现并修复的 bug（重要）
- **pinia deep reactive Proxy 导致 DataCloneError**：`workerSegments` 存进 `ref()` 后数组元素被深度 reactive 化（Proxy）；`saveEditDraft` 里 `[...userSegments]` 是浅拷贝，Proxy 元素无法 structured clone → **草稿 IDB 落盘完全失败**（首次 e2e 实测暴露：IDB drafts 空、仅后端 autosave 成功）。
- 修复：`userSegments.map((s) => ({ ...s }))` 逐段解构为纯对象（`src/utils/storage.ts`）。这是 IDB drafts 首次存储对象数组，此前只存过 number 数组未暴露。
- 验证：修复后 e2e 实测 IDB 草稿成功写入（editText 714825 / baseline 714808 / userSegments 2 段）。

### 9.5 二期建议（达标 ≤1s 所需，未实施）
1. **CM 初始化异步化/预创建**：viewCreate 1.8s（forced layout）是最大项，需 async EditorView 挂载（首帧先出骨架/loading，CM 后台创建）或大文档专用轻量渲染策略——影响查看态与编辑态，属大文档通用性能专项，独立规划。
2. **ensureEditor 懒构建**：bToAMap/buildDiffSegMap 仅在首次用户编辑时构建（恢复瞬间不需要），mapDiffSegs 91ms 可延后。
3. **装饰分片 dispatch**：diff 层 buildDecoSet 对几十万段分片渲染，首帧更快（当前 decoDiff 6.6ms 已很快，收益有限）。
4. **Sidebar 变更列表虚拟化**（若 contexts 上万）与 `flushEditsSync` 主线程全量 classify（导出/侧边栏跳转路径）独立修复。
