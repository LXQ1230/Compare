## 1. 项目概述

### 1.1 目标

一个支持 **txt、docx、md** 三种格式的文档对比工具，生成交互式 Web 对比报告。核心能力包括字符级精确对比、双视图模式（统一视图 + 分栏视图）、编辑模式（三方 Diff 区分原始变更与用户编辑）、版本化保存、多格式导出。

### 1.2 核心特性

| 特性 | 说明 |
|------|------|
| **多格式支持** | txt（含多编码自动检测）、docx（纯文本提取）、md（剥离标记后纯文本对比） |
| **字符级 Diff** | google-diff-match-patch，字符级精确对比 + 语义清理，永不降级 |
| **双视图模式** | 统一视图（差异内嵌单一文本流）+ 分栏视图（原文/修改左右对照同步滚动），工具栏一键切换 |
| **编辑模式** | 三方 Diff 区分原始变更与用户编辑，合并分类 + 单层渲染 |
| **版本化保存** | 手动保存创建带时间戳版本快照，最近 10 个版本可恢复，自动清理 |
| **导出** | TXT（统一 diff 格式 / 干净文本）、MD、HTML（带标注 / 干净文本） |
| **纯文本对比** | 提取纯文本内容进行对比，不做格式/排版解析，不解析图片/表格 |
| **单页路由** | Vue Router 双路由（`/` 选择页 + `/report` 报告页），无跨窗口通信 |

### 1.3 范围边界

| 包含 | 不包含 |
|------|--------|
| txt/docx/md 纯文本字符级对比 | 格式变更检测（字体/字号/颜色等） |
| docx 纯文本提取 | docx 内图片/表格/页眉页脚/批注 |
| md 剥离标记后纯文本对比 | md 原始源码对比 |
| 编辑模式 + 三方 Diff + 版本管理 | PDF 导出 |
| TXT/MD/HTML 导出 | docx 写回 |
| 同格式两两对比 | 跨格式对比（docx vs md 等） |

### 1.4 与 IDML 对比工具的关系

本工具是一个**独立的、全新的项目**，与 IDML 对比工具（`D:/Desktop/IDML/`）并存。两者：

- **共享技术栈**：Vue 3 + TypeScript + Vite 前端 / Python 后端（但新工具用 FastAPI 替代 http.server）
- **共享部分架构思路**：流式 diff、双视图、编辑模式、虚拟滚动等经过验证的模式可直接复用
- **核心差异**：新工具聚焦纯文本对比（无格式/排版元数据），后端更轻量（纯 Python，无 Node.js），架构更简洁（单页路由，无跨窗口通信）

## 4. 文档解析

### 4.1 通用策略

所有格式统一提取为**纯文本**，不做格式/排版解析。提取后送入 diff 引擎做字符级对比。

### 4.2 txt 解析

```
读取文件
  ├─ BOM 检测（EF BB BF → UTF-8, FF FE → UTF-16 LE, FE FF → UTF-16 BE）
  ├─ 尝试 UTF-8 严格解码
  │   ├─ 成功 → 返回文本
  │   └─ 失败 → chardet 自动检测
  │         ├─ 置信度 ≥ 90% → 自动应用
  │         └─ 置信度 < 90% → 弹出预览确认框（3 个候选编码 + 文本预览）
  └─ 返回纯文本内容
```

### 4.3 docx 解析

```
读取文件
  ├─ 文件头校验（ZIP 魔数 PK\x03\x04）
  ├─ 内部结构验证（word/document.xml 存在）
  ├─ 失败 → 拒绝并提示原因
  │
  └─ python-docx 提取
       ├─ 遍历 document.xml 中所有段落
       ├─ 提取每个 run 的文本内容
       ├─ 段落之间保留换行分隔
       ├─ 跳过图片/表格/页眉页脚/批注
       └─ 返回纯文本内容
```

### 4.4 Markdown 解析

**全量剥离标记 + 保留段落结构：**

| 元素 | 处理 |
|------|------|
| 标题 `#` 标记 | 删除，标题后加空行 |
| `**粗体**` `*斜体*` `` `代码` `` `~~删除~~` | 删除标记符号，保留内部文字 |
| `[文字](url)` | 只保留"文字" |
| `![alt](url)` | 只保留 alt 文本 |
| 列表 `-` `*` `1.` 标记 | 删除，项之间保留换行 |
| 引用 `>` | 删除前缀，保留文字 |
| 代码块 ` ``` ``` ` | 保留代码文字，去反引号围栏 |
| 分隔线 `---` `***` | 整行删除 |
| 表格 `\|` 分隔符 | 保留单元格文字，空格分隔，行间换行 |
| HTML 标签 `<tag>` | 删除标签，保留内部文字 |
| `<br>` `<br/>` | 替换为换行 |
| **段落空白行** | 保留——文本的语义分隔 |
| **连续空行** | 合并为单空行 |

### 4.5 文件大小

| 限制类型 | 策略 |
|------|------|
| **硬限制** | 无硬数值限制 |
| **资源感知** | 估算内存需求（解压后文本大小 × 4），对比可用 RAM。需求 > 70% 可用 RAM 时黄色提示；需求 > 100% 可用 RAM 时橙色警告但允许继续 |
| **极端场景** | 支持文本量达数千万字符的 1GB 级 docx 文档 |

## 5. Diff 引擎

### 5.1 选型：google-diff-match-patch

- **Python 版**运行在服务端，通过 NDJSON 流式 API 返回 diff 结果
- 字符级对比 + `diff_cleanupSemantic()` 语义清理
- 内置 patch 生成能力：`patch_make(baseline, current)` 产出增量 Patch 列表，用于编辑模式追踪用户变更

### 5.2 精度要求

**绝对不允许降级。** 必须始终输出字符级精确 diff。

| 策略 | 说明 |
|------|------|
| **禁用超时** | 不设 diff 超时限制，字符级精确比对到底 |
| **等待策略** | 不设等待上限，服务端跑多久等多久 |
| **进度提示** | 单端点 `/api/compare` 阶段感知流式推送：解析阶段 → diff 阶段 |

### 5.3 核心流程

```
原始文本 + 修改文本
       ↓
diff_match_patch.diff_main(orig, mod, timeout=0)  →  永不超时
       ↓
diff_match_patch.diff_cleanupSemantic()
       ↓
diffResultToSegments()  →  Segment[] (合并相邻单字符操作为 mod)
       ↓
构建 ChangeContext[]
       ↓
NDJSON 流式返回: phase → meta → segments chunk ×N → done
```

### 5.4 DiffOp 类型

```typescript
interface DiffOp {
  type: '=' | '+' | '-';
  text: string;
}

interface Patch {
  diffs: DiffOp[];
  start1: number;
  start2: number;
  length1: number;
  length2: number;
}
```

## 6. 数据模型

### 6.1 Segment

```typescript
interface Segment {
  text: string;
  operation: 'add' | 'del' | 'mod' | 'none';    // 纯文本无 format 类型
  origin: 'original' | 'user';
  side?: 'old' | 'new';
  ci?: number;   // change index，用于跳转
}
```

### 6.2 渲染映射（6 色体系）

纯文本对比无格式变更（format），共 5 种 operation × origin 组合：

| operation | origin | side | CSS 类名 | 说明 |
|-----------|--------|------|----------|------|
| add | original | — | `seg add` | 原始新增（绿色） |
| del | original | — | `seg del` | 原始删除（红色+删除线） |
| mod | original | old | `seg mod-old` | 原始修改-旧值（红底+删除线） |
| mod | original | new | `seg mod-new` | 原始修改-新值（绿底+加粗） |
| add | user | — | `seg user-add` | 用户新增（暖橙底+加粗） |
| del | user | — | `seg user-del` | 用户删除（紫底+删除线） |
| mod | user | old | `seg user-mod-old` | 用户修改-旧值 |
| mod | user | new | `seg user-mod-new` | 用户修改-新值 |
| none | — | — | `seg` | 无差异文本 |

### 6.3 合并分类 + 单层渲染（编辑模式）

纯文本下用**合并分类 + 单层渲染**，替代 IDML 工具的两层叠加：

1. 进入编辑模式时，将当前文本保存为**基线快照**（`baseline`）
2. 每次编辑触发后（800ms debounce），调用 `patch_make(baseline, current)` → 得到 `Patch[]`
3. 遍历所有 Segment，对每个字符位置判断：被 Patch 覆盖 → 重新分类为 `user-*`；未被覆盖 → 保持原始 diff 类型
4. 生成新的合并 Segment[] → **单层渲染**（与查看模式共用同一渲染管线）

**为什么纯文本下两层不需要：** 每个字符位置只有一个维度（文本内容），操作类型可线性推算，不存在"既被格式变更标记又被用户删除"的多维度冲突。

### 6.4 颜色覆盖优先级

| 原始标记 | 用户操作 | 界面显示 | 撤销后 |
|----------|----------|----------|--------|
| add（绿增） | 删除 | `user-del`（紫底+删除线） | 恢复绿色新增 |
| add（绿增） | 修改 | `user-mod` | 恢复绿色新增 |
| del（红删） | 恢复/新增 | `user-add`（暖橙底+加粗） | 恢复红色删除 |
| del（红删） | 修改 | `user-mod` | 恢复红色删除 |
| mod（红绿修改） | 再次修改 | `user-mod` | 恢复原始红绿修改标记 |
| none（无标记） | 新增 | `user-add`（暖橙底+加粗） | 恢复纯文本 |
| none（无标记） | 删除 | `user-del`（紫底+删除线） | 恢复纯文本 |
| none（无标记） | 修改 | `user-mod` | 恢复纯文本 |

### 6.5 ChangeContext

```typescript
interface ChangeContext {
  index: number;         // 第 N 处
  total: number;         // 共 M 处
  type: 'add' | 'del' | 'mod';
  before: string;        // 前文上下文
  highlight: string;     // 变更文字
  after: string;         // 后文上下文
}
```

## 7. HTTP API 端点

### 7.1 端点总览

| 方法 | 路径 | 功能 | 请求体 | 响应 |
|------|------|------|--------|------|
| POST | `/api/compare` | 上传文件并执行对比 | multipart: fileA + fileB | NDJSON 流式 |
| POST | `/api/autosave` | 保存/读取编辑草稿 | `{action, key, html?, text?, time?}` | `{success, saved?}` |
| POST | `/api/versions/save` | 创建版本快照 | `{session_key, text, html}` | `{success, version}` |
| GET | `/api/versions/list` | 列出当前会话版本 | query: `session_key` | `{versions: [...]}` |
| POST | `/api/versions/restore/{version_id}` | 恢复指定版本 | `{session_key}` | `{success, text, html}` |
| GET | `/api/health` | 健康检查 | — | `{status: "ok"}` |

### 7.2 核心端点：POST /api/compare

**阶段感知流式推送：**

```
POST /api/compare (multipart: fileA + fileB)

响应（NDJSON 流式）：

chunk 1: {"type":"phase","stage":"parsing","detail":"正在解压文档A...","progress":0.3}
chunk 2: {"type":"phase","stage":"parsing","detail":"正在提取文本B...","progress":0.8}
chunk 3: {"type":"phase","stage":"diffing","detail":"正在执行字符级对比...","progress":0.0}
chunk 4: {"type":"meta","stats":{"total":582,"add":152,"del":89,"mod":341},"totalChunks":42}
chunk 5-N: {"type":"segments","index":0-41,"data":[...]}
chunk N+1: {"type":"done"}
```

- 一个 HTTP 往返完成全部流程
- 解压/提取阶段有独立的进度反馈（`phase` chunk）
- diff 阶段复用 IDML 工具的 NDJSON segments 流式推送

### 7.3 统一错误信封

所有 API 错误返回同一格式：

```json
{
  "error": true,
  "severity": "blocking",
  "title": "文件无法打开",
  "message": "无法解压 docx 文件，该文件可能已损坏。",
  "detail": "ZIP header at offset 0: expected PK\\x03\\x04, got \\x00\\x00"
}
```

| severity | 前端呈现 | 用户操作 |
|----------|----------|----------|
| `blocking` | 模态弹窗 | 确认 → 返回选择页 |
| `warning` | 顶部黄色提示条 | 可关闭，不阻塞 |
| `info` | 底部 toast，3s 消失 | 无 |

## 8. 前端路由与状态管理

### 8.1 路由设计

单页应用，vue-router 两条路由：

```
/         → 选择页（文件上传、格式校验、编码确认）
/report   → 报告页（双视图、编辑、搜索、导出）
```

刷新 `/report` 时从 IndexedDB + localStorage 恢复数据。无数据则重定向回 `/`。

### 8.2 状态管理（Pinia）

```
stores/
├── compare.ts      → 对比数据：segments、contexts、原文文本、统计、文件信息
├── editor.ts       → 编辑状态：isEditing、baseline、patches、autosave
├── search.ts       → 搜索状态：query、options、matches、activeMatch
├── view.ts         → 视图状态：viewMode (unified/split)、sidebar、minimap
└── version.ts      → 版本列表、当前版本ID
```

### 8.3 数据持久化

```
localStorage（固定键名，无 sessionId）：
  ├─ compare_meta             → {fileA, fileB, stats, timestamp}
  ├─ compare_autosave         → {html, text, time}
  └─ compare_versions         → [{id, label, time}]（版本索引）

IndexedDB（数据库 CompareDB）：
  ├─ store: segments          → 当前对比的全部 segments（分段存储）
  └─ store: contexts          → 当前对比的全部 contexts
```

**生命周期：**

| 事件 | 行为 |
|------|------|
| **新对比开始** | 清空旧 IndexedDB，写入新数据；覆盖 localStorage |
| **页面刷新** | URL 是 `/report` → 从 IndexedDB + localStorage 恢复。有 autosave → 恢复编辑。无数据 → 重定向 `/` |
| **[← 新建对比]** | 导航到 `/`，所有旧数据保留（不做清空操作） |
| **新对比完成** | IndexedDB 和 localStorage 自然覆盖 |
| **清除缓存** | 侧边栏底部"清除缓存"按钮 → 清空 IndexedDB + localStorage |

## 15. 边界情况

### 15.1 空文件与完全相同的处理

**不特殊处理 — diff 引擎自然计算 + 轻量标注：**

| 场景 | 行为 |
|------|------|
| **原始文档为空** | diff 输出全文标记为"新增"，侧边栏标注"原始文档为空" |
| **修改文档为空** | diff 输出全文标记为"删除"，侧边栏标注"修改文档为空" |
| **两份完全相同** | 全文无标记，顶部蓝色持久提示条"两份文档完全相同，未发现差异" |
| **两份均为空** | diff 输出空，toast "两份文档均为空，无法对比"，2 秒后自动跳回 `/` |

> 空文本是合法输入而非错误。diff 引擎不需要前置判断来特殊处理。

```
用户上传文件
    │
    ├─ 扩展名不是 .txt / .md / .docx
    │   └─ ❌ 拒绝："不支持的文件格式"
    │
    ├─ 扩展名是 .txt 或 .md
    │   └─ 读取前 512 字节 → 检测可读文本比例
    │       ├─ ✅ 无效字符 < 10% → 接受
    │       └─ ❌ 含大量二进制 → 拒绝
    │
    └─ 扩展名是 .docx
        └─ 读取文件头 4 字节 → ZIP 魔数检测
            ├─ ✅ PK\x03\x04 + 内部有 word/document.xml → 接受
            └─ ❌ 无效 → 拒绝
```

### 16.2 编码检测

```
读取文件
  ├─ BOM 检测 → 确定性判断
  ├─ UTF-8 严格解码 → 成功则通过
  └─ chardet 自动检测
       ├─ 置信度 ≥ 90% → 自动应用
       └─ 置信度 < 90% → 弹出编码预览确认框
```

## 21. 技术决策记录

### ADR-1：FastAPI 替代 http.server

- **决策**：FastAPI + uvicorn 替代 Python 标准库 `http.server`
- **原因**：`StreamingResponse` 流式 NDJSON 原生支持、自动参数校验、OpenAPI 文档
- **代价**：额外 pip 依赖，便携包 +~10MB

### ADR-2：单页路由替代双窗口

- **决策**：vue-router `/` ↔ `/report` 单页路由，替代 IDML 工具的独立窗口 + postMessage
- **原因**：消除弹窗拦截痛点；消除跨窗口通信复杂度（~1000 行代码）
- **代价**：选择页在后台不存活，但符合线性使用流程

### ADR-3：纯文本提取

- **决策**：所有格式提取为纯文本对比，不做格式/排版解析
- **原因**：用户需求；大幅降低系统复杂度；docx 写回自然放弃
- **代价**：格式信息丢失，无法写回 docx

### ADR-4：字符级 Diff

- **决策**：google-diff-match-patch 字符级精确对比，永不超时
- **原因**：用户明确要求"必须精确"；久经考验
- **代价**：极端大文本耗时较长，流式进度缓解

### ADR-5：合并分类 + 单层渲染

- **决策**：编辑模式合并分类单层渲染，替代 IDML 工具的两层叠加
- **原因**：纯文本无格式/排版元数据冲突，分类无歧义；查看/编辑共用渲染管线
- **代价**：每次编辑需重新分类 Segment，但纯文本 O(n) 可接受

### ADR-6：版本化 Autosave

- **决策**：无独立备份系统，版本化保存（最近 10 个版本）替代
- **原因**：备份需求由版本管理消化；用户心智模型更简单
- **代价**：无双份备份安全网，但纯文本数据可随时复制

### ADR-7：无硬文件大小限制

- **决策**：资源感知警告替代固定 GB 上限
- **原因**：固定上限浪费高配机器，低配机器不够用
- **代价**：需 `psutil` 获取系统内存

### ADR-8：零 PDF 依赖

- **决策**：不支持 PDF 导出，纯 Python 后端
- **原因**：纯文本场景 PDF 边际价值有限；去掉 Node.js 大幅简化分发
- **代价**：有 PDF 需求的用户需自行浏览器打印

### ADR-9：零设置面板

- **决策**：无设置面板，参数写为代码常量
- **原因**：纯文本对比无可配色主题/备份路径等用户配置项
- **代价**：需改代码才能调整参数

### ADR-10：复制即用型便携包

- **决策**：便携 Python + 预装依赖 + 前端 dist + start.bat
- **原因**：比 PyInstaller 干净，比脚本安装方便
- **代价**：包体 ~60MB，需按 OS 分别制作

### ADR-11：模式驱动导出

- **决策**：查看模式 → 带标注导出，编辑模式 → 干净导出
- **原因**：模式 = 用户在看什么，导出自然对齐
- **代价**：查看模式无法直接导出干净文本
