# IDML 支持 + 排版效果级呈现 — 设计方案

> 分支：`feature/idml-support` ｜ 日期：2026-08-05
> 状态：方案已确认（用户四问收敛），待实施

## 1. 需求定义（已确认）

| 维度 | 决策 |
|---|---|
| 格式 | 支持 .idml 上传与对比（与 txt/docx/md 并存） |
| 排版呈现 | **效果级**（非像素级）：Warichu 双排小字 + 竖排 + 字体/字号/颜色/粗斜 + 行距/缩进 |
| 查看模式 | ✅ 完整呈现上述排版属性 |
| 编辑模式 | CodeMirror 线性编辑（割注显示为小字号内联文本），折行仅在渲染层 |
| 样式与 diff | 样式**不参与 diff**（文本相同即无差异），样式作附着层透传 |
| 写回 IDML | 搁置（本期不做 save_idml） |
| 验收 | 与 InDesign 导出 PDF 对照（fixtures/7.pdf） |

## 2. 实证结论（fixtures/7.idml + 7.pdf 比对）

### 2.1 双排小字 = InDesign Warichu（割注）

```xml
<CharacterStyleRange PointSize="28" Warichu="true" WarichuSize="40" WarichuLineSpacing="3">
    <Content>諸羅漢名本或用梵語或用華語今...</Content>
</CharacterStyleRange>
```

- 全文件 76 处：`WarichuSize=40`×75 + `WarichuSize=60`×1，`WarichuLineSpacing=3`
- **割注字号 = PointSize × WarichuSize/100**（28×0.4=11.2pt、28×0.6=16.8pt，PDF 实测吻合）
- **文本线性存储，渲染时折双列**（页 5：「諸羅漢名本或用梵語或用華語今」→ 右列 7 字 + 左列 7 字）

### 2.2 割注折行规则（页 5+6 实证，24 字割注全流向）

IDML 两个相邻 Warichu CSR（9 字 + 15 字 = 24 字）被 InDesign **合并渲染**为连续割注流：

| 位置 | 列 | 内容 | 字数 |
|---|---|---|---|
| 页5 | 右列 x=99 | 諸羅漢名本或用 | 7 |
| 页5 | 左列 x=85 | 梵語或用華語今 | 7 |
| 页6 | 右列 x=1036 | 止酌列五尊 | 5 |
| 页6 | 左列 x=1022 | 者以例其余 | 5 |

**折行规则（实证结论）**：
- 相邻 Warichu CSR 视为连续割注流，**跨 CSR 边界合并折行**
- 每列容量 ≈ 行高空间 / 割注字号（页5 每列 7 字、页6 每列 5 字 → 列容量受所在行行高约束，非固定值）
- 竖排阅读顺序：右列 → 左列 → 下一组续列（页6 为溢出续排）
- 溢出跨行/跨页续排（页5 → 页6）

> 渲染近似策略：合并相邻割注 → 按「列容量 = floor(行高/割注字号)」折列，列容量不足时开新列组（效果级近似，以 PDF 对照验收）。

### 2.3 文档排版特征

- 竖排：`<StoryPreference StoryOrientation="Vertical" StoryDirection="LeftToRightDirection" />`
- 正文 28pt 思源宋体，Leading 43（行距系数 ≈ 1.536）
- 句号专用 CSR：悬挂 `BaselineShift="-9.2"`、`FillColor=Color/Registration`（校勘标注用彩色）
- 首行缩进 `FirstLineIndent="56.69291338582678"`（约 2 字）
- 题记 20/24pt、书名 62.6pt；PSR 带 ParagraphShading/Border（本期不呈现）

### 2.4 字体名分布（10 种，映射表依据）

| IDML 字体名 | 出现次数 | 本机可用 | 映射策略 |
|---|---|---|---|
| 思源宋体 CN | 2098 | ✅ SourceHanSerif | 正文主力，直接映射 |
| Adobe 宋体 Std | 39 | ✅ | 标题 |
| 仿宋 (OTF) | 21 | ✅ simfang | 偈颂 |
| 思源黑体 CN | 17 | ✅ SourceHanSans | 强调 |
| 方正粗雅宋长_四川石油_GBK | 6 | ❌ | 回退思源宋体 + 记录警告 |
| Minion Pro | 3 | ❌ | 回退 serif 西文 |
| 经书粗宋1/2/3 | 7 | ❌ | 回退思源宋体 + font-weight 700 |
| 汉仪大宋繁 | 1 | ❌ | 回退思源宋体 |

> 映射策略三级：精确匹配 → 前缀匹配（思源宋体→SourceHanSerif）→ 回退链（serif/sans-serif）+ 不可用告警。字体名映射表放 `parsers/font_map.py`，可配置扩展。

### 2.5 颜色映射（Resources/Graphic.xml，16 色全 CMYK Process）

- 全部 `Model="Process" Space="CMYK"`，如 `ColorValue="0 0 100 0"`（黄）
- `Color/Registration` = 校勘标注专用 → 渲染 #C00000（醒目红）
- CMYK → RGB 标准公式（无 ICC 校准，效果级够用）
- CSR 引用：`FillColor="Color/C=15 M=100 Y=100 K=0"`（校勘红）、`FillColor="Color/Registration"`

## 3. 总体架构

```
IDML ──► parsers/idml_parser.py（新增）
          │  产出结构化解析结果：
          │    text: str（参与 diff 的纯文本，竖排转为逻辑顺序）
          │    spans: StyleSpan[]（样式区间，字符级偏移）
          ▼
main.py /api/compare：diff_texts(text_a, text_b)（零改动）
          │  diff 后按位置把 spans 切分附着到 segments
          ▼
NDJSON segments 增加可选字段 style（样式区间数组）
          ▼
前端：
  查看模式 → segmentRenderer 渲染 <span style="...">（竖排容器 + Warichu 双列）
  编辑模式 → CodeMirror 内联小字号文本（无需特殊逻辑）
```

## 4. 数据模型

### 4.1 后端 StyleSpan（新）

```python
@dataclass
class StyleSpan:
    start: int      # 在 text 中的字符偏移（含）
    end: int        # 字符偏移（不含）
    font: str = ""          # 字体名（映射到本机字体）
    size_pt: float = 28.0   # 字号 pt
    bold: bool = False      # FontStyle Heavy/Bold → bold
    color: str = "#000000"  # FillColor 映射（Registration→红，CMYK→hex）
    warichu: bool = False   # 割注标记
    warichu_size: int = 0   # 割注百分比（40/60）
    baseline_shift: float = 0.0  # 悬挂等基线偏移
```

### 4.2 Segment 扩展（可选字段）

```typescript
export interface StyleRange {
  start: number        // 相对 segment.text 的字符偏移
  end: number
  font?: string
  sizePt?: number
  bold?: boolean
  color?: string
  warichu?: boolean
  warichuSize?: number
  baselineShift?: number
}

export interface Segment {
  // ...现有字段
  style?: StyleRange[]  // 仅 IDML 文件携带；txt/docx/md 无此字段，零影响
}
```

> 关键设计：style 是**可选字段**，非 IDML 文件完全不受影响（无字段、无解析、无体积开销）。

## 5. 解析器设计（parsers/idml_parser.py）

复用 JidouInject 成熟骨架（已实证 8 本经书），扩展样式提取：

### 5.1 流程

```
ZIP 校验（PK\x03\x04 头，与 docx 同套路）
  → 防 zip bomb：解压总字节上限（如 200MB）+ 文本总量上限（如 200 万字）
  → designmap.xml → StoryList 顺序
  → 逐个 Story XML（defusedxml 防 XXE）
  → PSR → CSR → Content 遍历（含 html.unescape 实体解码、自闭合空段、ACE 指令）
  → 字符级样式游标 → 合并连续同样式为 StyleSpan
  → 装饰性 Story 过滤（<50 净字跳过，页眉/书名等）
  → 自检：正则交叉验证零丢失（JidouInject _verify_extraction 同款）
```

### 5.2 样式提取（CSR 属性 → StyleSpan）

| IDML 属性 | 映射 | 说明 |
|---|---|---|
| `AppliedFont`（Properties 内） | font | 字体名映射表归一化（§2.4） |
| `PointSize` | sizePt | 28 → 28 |
| `FontStyle="Heavy"/"Bold"` | bold | 粗体 |
| `FillColor="Color/Registration"` | color=#C00000 | 校勘标注（§2.5） |
| `FillColor="Color/C=15 M=100 Y=100 K=0"` | color=hex | CMYK→RGB 换算 |
| `Warichu="true"` + `WarichuSize` | warichu + warichuSize | **割注核心** |
| `BaselineShift` | baselineShift | 句号悬挂 -9.2 |
| `Leading`（PSR/Properties） | 段落级 lineHeight | 43 → 1.536 系数 |

### 5.3 段落级属性（PSR）

- `Leading` → 行高系数（leading/size）
- `FirstLineIndent` → text-indent（pt→px，96dpi 换算 ×1.333）
- 竖排：Story 级 `StoryOrientation="Vertical"` → 整篇 writing-mode
- 段前/段后距（SpaceBefore/SpaceAfter）→ margin 简化映射（本期可选）

### 5.4 文本序列化（竖排 → 逻辑顺序）

IDML 中竖排文本在 Story XML 内**已是逻辑阅读顺序**（段落连续存储），
故 text 直接按段落拼接（`\n` 分隔），无需特殊处理。竖排仅影响渲染层。

### 5.5 Warichu 合并与折行算法（核心，实证驱动）

解析时产出的割注片段不做物理折行（保持线性文本 + warichu 标记），
折行延迟到**渲染层**（前端），理由：
1. 文本参与 diff/编辑/持久化必须保持线性（与 XML 存储一致）
2. 折行参数（列容量）取决于渲染上下文（行高），解析期无法确定

后端仅做**割注片段合并标注**：
```
相邻 Warichu CSR（同段落、无缝衔接）→ 合并为单一割注单元
  割注单元 = { text: str, size_pt, warichu_size, 起始偏移 }
```
前端渲染时对割注单元执行折行（见 §6.3）。

### 5.6 体积控制（⚠️ 深度挖掘新增，497 级实测必须）

**实证数据（497：63 万字）**：
- 解压后 170.9MB（287B/字）、CSR 53.4 万个
- 原始 style（每 CSR 一 span）≈ 30MB —— **不可接受**
- **连续合并后 55,410 span（10.4%）≈ 3MB** —— 可接受

**策略（后端强制）**：
1. **连续合并**：相邻 CSR 若样式签名相同（PointSize|FontStyle|字体|Warichu|颜色）→ 合并为单 span
2. **签名驱动**：合并以「样式签名」为键，非字符级（避免 497 的逐字 CSR 爆炸）
3. **span 瘦身**：只传非默认值（font/size/color 与正文默认相同则省略字段）
4. 验收阈值：497 级 style 数据 ≤ 正文的 5%（3MB/63 万 ≈ 4.8B/字）

### 5.7 ⚠️ 段落边界：Br 驱动而非 PSR（深度挖掘，推翻 JidouInject 假设）

**实证（7.idml 主 Story）**：PSR 仅 **3 个**，Br **72 个** → 段落由 `<Br/>` 驱动，PSR 只是样式分组。

- JidouInject 模型「PSR=段落」**不成立**——解析器必须在 `<Br/>` 处插入段落标记，PSR 仅提供段落级样式上下文（Leading/缩进）
- 7.idml 无 U+3000（与 JidouInject 经书不同）——**不可假设 U+3000 剥离**，按实际文件处理；U+3000 的语义由 diff W 规则统一处理（空白分隔符）
- Content 无内嵌 `\n`（4132 个 Content 全部无换行）→ 换行唯一来源是 Br

### 5.7.1 ⚠️ 段落标记选择：U+2029 而非 \n（第六轮实证，diff 语义关键）

**问题**：若 IDML 段落用 `\n` 拼接，W 空白归因规则会把 `\n` 当排版空白——
实测（diff_texts）：
- 段落合并（A 两段 → B 一段，删 \n）→ **完全隐藏，stats=0**，A/B 段落结构差异消失
- 段落拆分（A 一段 → B 两段，加 \n）→ 显示为 add（不对称）

对 IDML 竖排渲染的后果：**B 侧（修改版）段落边界丢失**，渲染层无法重建竖排列结构。

**方案（已实测验证）**：IDML 段落分隔符用 **U+2029（PARAGRAPH SEPARATOR）** 而非 `\n`：
- U+2029 不在 `_WS_CHARS`（diff_engine 实测：段落合并显示 del、内容相同完整保留）✓
- 渲染层将 U+2029 映射为竖排「另起一列」/ 横排「换行」
- 编辑态：CodeMirror 中 U+2029 正常处理（不可见控制符，或渲染为段落间隙）
- 导出：TXT/MD 导出时 U+2029 → `\n`（exporters 统一转换）

### 5.7.2 解析性能与 ReDoS 安全实测（第六轮）

**性能（497：63 万字，单 Story 167MB 解压后）**：
- 读取+解码 167MB：**0.29s**；PSR 正则 1.34s（602 个）；CSR 正则 0.20s（534,174 个）
- **总计 ~1.8s，无性能瓶颈**；正则方案可行

**ReDoS 安全**（5 万字符恶意输入：未闭合标签/深嵌套）：
- PSR/CSR/Content 正则最大 **563ms**（深嵌套 CSR），无灾难性回溯 ✓
- XML 编码统一 UTF-8（497/7 均确认 `encoding="UTF-8"`）✓


### 5.8 ⚠️ style 附着算法：diff 偏移映射（深度挖掘）

后端 `diff_texts` 输出的 segments **无偏移信息**，无法直接映射 StyleSpan（基于全文偏移）。
**实现方案**：解析后把 text + spans 传给 diff 阶段，diff 时同步维护 A/B 两侧游标：

```
遍历 raw_diffs，累积 a_pos / b_pos：
  EQUAL:     spans 切分 → segment(取 A 侧 span)，a_pos+=len, b_pos+=len
  DELETE:    segment 取 A 侧 span（del），a_pos+=len
  INSERT:    segment 取 B 侧 span（add），b_pos+=len
  MOD(old):  segment 取 A 侧 span，a_pos+=len
  MOD(new):  segment 取 B 侧 span，b_pos+=len
```
span 切分：对 segment 区间 [a_pos, a_pos+len) 做二分查找，切出子区间并转 segment 内偏移。

## 6. 渲染设计

### 6.1 查看模式（segmentRenderer.ts / UnifiedView / SplitView）

- **段落容器**：`writing-mode: vertical-rl`（竖排）/ `horizontal-tb`（横排）
- **行高**：`line-height: 1.536`（Leading 系数）
- **字符样式**：segment.text 内按 style 区间切分为 `<span>`：
  - `font-family` / `font-size` / `font-weight` / `color`
- **Warichu 割注**（核心效果，详见 §6.3）
- **悬挂句号**：`BaselineShift -9.2` → `position: relative; top: 9.2pt`（或 vertical-align）
- **⚠️ A/B 侧样式归属（深度挖掘新增）**：
  - SplitView：left 用 A 侧 style，right 用 B 侧 style（天然分离）
  - UnifiedView：**none 段取 A 侧样式**（以原文件为准）；add 段取 B 侧；del/mod-old 取 A 侧
  - 后端附着时按 segment 的 side/operation 决定取哪侧 style

### 6.2 编辑模式（CodeMirrorDiff）

- 割注文本按**普通字符**参与编辑（XML 线性存储，天然正确）
- **⚠️ 现状缺口**：CodeMirrorDiff 仅有全局 fontSize（--editor-font-size），无行内样式装饰
  - 需新增：`buildStyleDecos(segs)` → `Decoration.mark({ style: 'font-size:...;color:...;font-weight:...' })`
  - 与现有 diffField/userField 并行叠加（第 3 层 Decoration，只读不参与编辑语义）
- 段落级属性（行距/缩进/竖排）在编辑态不呈现 → 通过查看模式预览
- 竖排文档编辑时按横排线性文本（逻辑顺序），不呈现 writing-mode

### 6.3 Warichu 折行算法（渲染层，实证驱动）

**输入**：割注单元（合并后的线性文本 + size_pt + warichu_size）
**输出**：N 组双列（或双行）小字 HTML

```
算法（竖排容器内）：
  fontSize = size_pt × warichuSize / 100        # 11.2pt（40%）/ 16.8pt（60%）
  colCapacity = floor(lineHeight / fontSize)     # 每列容量（页5:7字，页6:5字）
  groups = []
  rest = text
  while rest 非空:
      col1 = rest[:colCapacity]
      col2 = rest[colCapacity:colCapacity*2]
      groups.append((col1, col2))
      rest = rest[colCapacity*2:]                # 溢出开新列组（跨行续排）
```

**HTML 结构（竖排）**：
```html
<span class="warichu" style="font-size: 11.2pt">
  <span class="warichu-pair">          <!-- 一组双列，右列 + 左列 -->
    <span class="warichu-col">諸羅漢名本或用</span>   <!-- 右列（先读） -->
    <span class="warichu-col">梵語或用華語今</span>   <!-- 左列（后读） -->
  </span>
  <span class="warichu-pair">          <!-- 溢出组：续排 -->
    <span class="warichu-col">止酌列五尊</span>
    <span class="warichu-col">者以例其余</span>
  </span>
</span>
```

**竖排实现要点**：
- 外层 `display: inline-flex; flex-direction: row`（列并排）
- 每列 `writing-mode: vertical-rl`（列内字符竖排）+ `flex-direction: column-reverse` 控制阅读序
- **⚠️ colCapacity 修正（深度挖掘）**：原公式 floor(行高/割注字号)=43/11.2≈3 与实证矛盾（页5=7、页6=5）。
  实证表明列容量**非固定值**且不受单一 Leading 决定（页5/页6 同文件同正文行高却不同列容量）。
  **修正策略**：渲染层实现时以「页5=7、页6=5」为锚点校准，提供兜底常量 `COL_CAPACITY_DEFAULT=7`；
  精确规则待后续用更多 PDF 样例反推，本期效果级近似即可
- **横排文档**：每列转为横向行，两组上下叠放（`flex-direction: column`）

**验证锚点**：7.pdf 页 5（7+7 两列）+ 页 6（5+5 续列）——渲染输出与 PDF 逐组比对。

### 6.4 竖排容器方向（StoryDirection 映射）

- IDML `StoryOrientation="Vertical"` + `StoryDirection="LeftToRightDirection"`
- 实证：页 5 右列（x=99）先读 → 竖排列序为**右→左**，符合 `vertical-rl`
- 实现：默认 `writing-mode: vertical-rl`；渲染后与 7.pdf 对照校准（若列序相反则改 `vertical-lr`）
- 横向：`horizontal-tb`

### 6.5 ⚠️ 段落分隔与竖排换行（深度挖掘新增）

- IDML 段落以 `\n` 拼接（§5.4），但竖排容器中 `\n` 的换行方向与横排不同
- **方案**：渲染层把 `\n` 转为段落级换行标记（竖排时语义为「另起一列」），
  不依赖 CSS `white-space: pre-wrap` 的默认行为
- 需在 segmentRenderer 中处理：`\n` → `<br class="para-break">` 或容器分段
- 验证：7.pdf 页 3 段落边界对照

### 6.6 ⚠️ 持久化链路 style 丢失（深度挖掘，最严重发现）

**两条链路均会丢 style，必须在方案中显式处理：**

**链路 1：版本历史（VersionHistory）**
- 现状：`saveVersion` 只存 `file_a_content/file_b_content`（纯文本）；恢复时
  `buildSegmentsFromTexts(a, b)` 用 `diffSafely` **本地重建 segments → style 必然丢失**
- 影响：IDML 版本回滚后排版呈现退化（只剩文本）
- **方案**：`VersionEntry` 增加可选 `styleA?/styleB?`（或存解析后的完整 spans）；
  saveVersion 从 compareStore 带出；restore 时重建 segments 后回填 style

**链路 2：编辑草稿（EditSessionDraft）**
- 现状：`draft.baseline` 是纯文本（`buildDocText` 过滤 phantom 段拼接），
  `userSegments` 是编辑分类结果（含 origin/operation，无原始 style 信息）
- 影响：恢复编辑会话后 styleDeco 无法重建（无 style 来源）
- **方案**：draft 增加 `baselineStyle?: StyleRange[]`（B 侧 style，随 baseline 一起存）；
  恢复时 `styleDeco` 基于 baselineStyle 构建
- 体积：StyleRange[] 已压缩（§5.6），IDB 容量可容纳

**原则**：style 必须与「它依附的文本」**同生命周期、同存储介质、同恢复路径**——任何重建
segments 的地方（版本恢复/草稿恢复/本地重建）都必须有 style 回填通道。

### 6.7 ⚠️ 导出链路样式断裂（深度挖掘第五轮）

**现状链路**：编辑模式导出 = `mergeLayers(original, user)` → `exportToHTML` → `renderSegmentsToHTML`。

**实证**：
- `mergeLayers` fast path（无用户编辑）用 `{...s}` 展开 → **style 天然保留** ✓
- 有编辑时 user 段（`classifyEdit` 产出，origin: 'user'）**无 style 字段** → 导出 HTML 中断裂
- `renderSegmentsToHTML` 目前完全不读 style（style 字段存在与否都不影响输出）

**决策点**：导出 HTML 是否带样式？
- **方案 A（推荐）**：导出 HTML 带样式——`renderSegmentsToHTML` 升级为读 style；
  user 段样式策略：**继承前邻字符样式**（编辑在割注内 → 新字也成割注，视觉连续）
- **方案 B**：导出保持纯文本 diff 标记（现状），style 只在应用内查看
- TXT/MD 导出不受影响（纯文本）

### 6.8 ⚠️ Story 结构与装饰过滤边界（深度挖掘第五轮）

**实证（275/461/7 三本经书）**：均为「**1 个正文 Story + N 个装饰 Story**」——
正文 Story 净字占绝对大头（6728/10504/14942），其余全部 <50 字。

**推论**：
- 跨 Story 顺序问题在真实经书中**不构成实际风险**（正文仅 1 个 Story）
- 但 **50 字过滤阈值是硬编码边界**：若某经书正文本身 <50 字（短经/残页）会被误杀
- **修正**：过滤规则改为「净字 < 50 **且** 非最大 Story」——正文 Story 必为净字最大者，
  保证短正文不被误过滤；多个正文 Story 的文档（章节拆分）记入后续（Story 筛选面板，需求 §6.4）

## 7. 传输与体积控制

- 样式区间合并（连续同样式 → 单个 span），避免逐字符传输
- 非 IDML 文件零开销；IDML 大文件（如 497 级）需验证 NDJSON 体积
  （粗估：1 万字符/万字约 2-4KB style 数据，可接受）
- 割注单元在解析层合并后传输（避免前端跨 segment 拼接）
- **⚠️ 497 级实测（§5.6）**：连续合并压到 10.4%（55K span / 3MB），
  若实测仍超阈值 → 二次方案：style 走独立分块通道（styleChunks）或按需加载
